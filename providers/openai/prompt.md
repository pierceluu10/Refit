OpenAI's REST API stays on `/v1`; breaking change mostly arrives through model retirements and endpoint shutdowns rather than new API versions. The deprecations page is the most important source: each entry names model snapshots or endpoints, a shutdown date and a recommended replacement. Report each announcement (or each group of models sharing one shutdown date) as a `model-retirement` change with the shutdown date as `effectiveDate`. Convention for this provider: put model ids in `affects.fields` prefixed with `model:` (for example `model:gpt-4o-2024-08-06`, listing both the alias and the dated snapshot when the page gives both), and put endpoints in `affects.operations` as method and path when known (for example `POST /v1/audio/translations`) or the path alone. Mention the recommended replacement in the title. Do not use `affects.versions` for model ids.

Whole APIs and products shut down too (the Assistants API in favour of the Responses and Conversations APIs, reusable prompts under `/v1/prompts`, the Evals API, the Realtime beta header `OpenAI-Beta: realtime=v1`). Use `endpoint-removed` when specific paths stop working and `product-shutdown` when a whole product or API family goes away. Parameter or request/response shape changes are `field-removed`, `field-renamed` or `other`.

The `openai` npm and PyPI SDKs follow semver, but their release notes sometimes flag a "breaking change in a minor release" in generated types; report those as `other` (or `sdk-major` for a real major) with `affects.sdk` set to `openai (npm) <version>` or `openai (pypi) <version>` and the changed types in `affects.fields`. The changelog mixes API changes with model launches, pricing, credits and dashboard news; new models and new optional features do not break code, so report only removals, shutdowns and behaviour changes that existing callers must react to. Ignore ChatGPT product news.

Stripe's API is versioned by date plus a release name, e.g. `2026-09-30.endive`. Callers pin a version with the `Stripe-Version` header, and each server-side SDK release pins the version that was current when it shipped (stripe-node from v12, stripe-python from v6, stripe-ruby from v9, stripe-php from v11; stripe-java, stripe-go and stripe-dotnet are fixed to it). Since `2024-09-30.acacia`, monthly versions are additive only and twice a year a new major (Acacia, Basil, Clover, Dahlia, Endive, ...) starts with a version that carries the breaking changes. A new major is an `api-version` change; each breaking item under it is its own change. Webhook endpoints and event destinations carry their own `api_version`, so payload changes there are `webhook-payload`.

The changelog marks every row Breaking or Non-breaking and links to a detail page with the exact params and migration steps; follow those links for breaking rows. In `affects`, put the API version the change lands in (`versions`), REST paths (`POST /v1/checkout/sessions`, `/v2/core/account_links`), params and object fields in dot form (`filters.countries`, `payment_method_types`), and stripe-node methods or types when the source names them (`stripe.webhooks.constructEvent`, `Stripe.V2List`). Rows in the `stripejs` category hit front-end Stripe.js and Elements code, not the server SDK; still report them.

SDK majors (stripe-node and its siblings ship one with each API major) are `sdk-major` when they rename or remove methods, change types, or drop a language runtime; the runtime support schedule on the SDK versioning page gives future drop dates. Ignore non-breaking additions (new params, enum values, resources, events), `.preview` and alpha/beta SDK releases unless a GA deadline is attached, and Dashboard-only features.

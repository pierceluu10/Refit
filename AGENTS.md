# Refit agent guide

## What Refit is building

Refit connects upstream API changes to the customer code that may need updating. The product goal is to monitor API contracts and selected documentation, find affected SDK usage, propose a migration, run the repository's checks in isolation, and open a human-reviewed draft pull request as Refit Agent.

Build toward a reliable agent for many API providers, with separate integrations and reviewable changes. Breaking changes are the first priority. Record other changes for review rather than generating speculative code updates. Prefer deterministic, explicitly configured migration rules; use AI only as a bounded assistant behind the existing evidence, budget, validation, and review gates.

## Product boundaries

- Read [READINESS.md](docs/READINESS.md) before describing support or choosing a feature. It records verified behavior and known gaps.
- Refit currently analyzes supported TypeScript and JavaScript SDK patterns. Provider support depends on observed SDK mappings and migration rules; OpenAPI compatibility alone does not mean a provider is ready for automatic fixes.
- Automatic edits must be limited to supported, evidence-backed migrations. Ambiguous code, API versions, request/response semantics, or webhook policies must stop for review.
- Validate changes in the existing isolated workflow. A passing command is evidence about that command, not proof of complete API or code coverage.
- App installation does not activate arbitrary repositories. Configuration and approval are explicit; workers, AI, and draft publication have separate settings. Refit never auto-merges.
- Keep credentials out of repository files and browser code. Never run a live vendor operation or paid model evaluation unless the task explicitly authorizes it and the configured budget allows it.

## Repository workflow

- Read the code and relevant tests before changing behavior. Follow existing architecture and keep changes focused.
- Preserve honest evidence boundaries in CLI output, reports, documentation, and pull requests. Do not claim a simulated test exercised a live provider.
- Run `npm test` after JavaScript or TypeScript changes, and run the relevant typecheck, formatting, and build checks for the touched code. Report what actually passed.
- Use conventional commit messages when committing requested project changes. Do not add co-author trailers.
- Update the relevant user-facing guide and readiness checkpoint when a feature changes supported behavior. Keep the root README short; put detailed setup and limitations in `docs/`.

## Hosted worker (Fly.io + Supabase)

The single-tenant hosted worker (`refit hosted serve`) runs as Fly app `refit-hosted` (region `iad`, one machine, 20 GB volume `refit_data` at `/data`) against the `refit-hosted` Supabase project (us-east-1). The deploy steps, the database role and day-to-day operation are in [Hosted onboarding](docs/HOSTED-ONBOARDING.md#deploy-on-flyio).

- Access: a teammate needs membership in the Fly organization that owns `refit-hosted` and in the Supabase organization that owns the project. Ask the owner for both; do not create new apps, projects or volumes to work around missing access. Run `fly auth login` yourself; agents never type credentials.
- Secrets live only in `fly secrets` (names: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `REFIT_WEBHOOK_SECRET`, `REFIT_SERVICE_TOKEN`, `REFIT_DATABASE_URL`, `REFIT_HOSTED_OWNER`, `OPENAI_API_KEY`, `OPENAI_MODEL`) and in the owner's private `~/.refit/hosted/` files. `fly secrets list` shows names and digests only. Never print, commit or paste secret values, the Supabase project ref or database passwords into this repository, which is intended to become public. Stage a value from a file or variable (`fly secrets set NAME="$(cat file)"`), never from a placeholder: a literal `<value>` is accepted and crashes the worker on boot.
- The worker connects as the `refit_hosted` role, which owns the `refit_*` tables. Do not switch it to `postgres` or the Supabase service key, add RLS policies or expose the tables through the Data API.
- Read-only checks are always safe: `curl https://refit-hosted.fly.dev/health`, `/status` with the service token, `fly status` and `fly logs -a refit-hosted`. `fly deploy`, `fly secrets set`, schema changes, `refit hosted approve` and `refit hosted retry` change the live service; with `--ai-patch` a job spends the owner's OpenAI budget and with `--publish-draft` it can open draft PRs. Do them only when the task asks.
- Hosted mode enrolls only `REFIT_HOSTED_OWNER`'s installations, and only repositories with a stored approval. Widening that to other accounts needs per-job isolation and an owner decision.

## Working in parallel

Several agents build and benchmark at once. To keep out of each other's way:

- One branch and one `git worktree` per task (`git worktree add -b feat/<name> ../Refit-<name> origin/main`). Never edit another agent's worktree or switch its branch. Run `npm ci` in a new worktree before tests.
- Stripe benchmarks run on GitHub Actions in `refit-dev/refit-bench` ([GitHub benchmarks](docs/GITHUB-BENCHMARKS.md)): dispatch `benchmark.yml` with a full pushed commit SHA, one repository per shard, and record the GitHub run id with the outcome. Its logs and artifacts are public, so never pass a key in an input; `-f ai=true -f ai_budget=<USD>` uses the owner's capped `OPENAI_API_KEY` secret and spends the OpenAI budget, so do it only when the task authorizes AI.
- Benchmarks with AI, or Shopify benchmarks, run on AWS with `node scripts/aws-benchmark.mjs` (profile `refit`, region `us-east-2`; the owner signs in with `aws login`, agents never handle credentials). Use a unique `--run <benchmark>-<date>-<agent>` id, pin `--commit`, keep `--hours` as low as the run needs, and always `collect` or `stop` the run when done. `launch` counts every agent's running shards against the account's vCPU quota and refuses to exceed it; wait rather than raising quotas or limits yourself.
- The AWS project has a monthly spend limit (see Billing) and is on the free plan (on-demand only). Ask before a run that needs more than the free on-demand quota (16 vCPUs, two `c7i.2xlarge`) or more than three hours, and before any `--ai` run, which also spends the OpenAI budget.
- Record benchmark outcomes in `docs/BENCHMARKS.md` with the run id, commit and command, as for local runs.

## Release and verification notes

- Work on a feature branch, open a PR against `main`, wait for CI (Node 22 and 24), then merge with a `feat: merge …` merge commit. Release commits are `chore: release Refit X.Y.Z …` and bump `package.json` and `package-lock.json`, add a dated `docs/READINESS.md` checkpoint, and update the guides they touch.
- Publish milestones as GitHub pre-releases titled only `vX.Y.Z`, from an annotated tag on the merge commit. Attach `refit-X.Y.Z.tgz` from `npm run package:cli -- --output <new-directory>` and its `SHA256SUMS`. Smoke-install the archive before publishing.
- Many suites are gated by environment variables and skip by default. Docker and real-SDK cases need `REFIT_DOCKER_IMAGE=node:22-alpine` plus `REFIT_NPM_PREPARE=1`, `REFIT_STRIPE_SDK=1` or `REFIT_OPENAI_SDK=1`. Report gated results separately from the default count.
- Recorded lockfile fixtures must stay byte-exact; keep them in `.prettierignore` rather than reformatting them.
- Benchmark results across every frozen set are consolidated in `docs/BENCHMARKS.md`. Frozen lists: Stripe `2026-10-14-stripe-repos.json` (100), `2026-10-15-stripe-heldout-repos.json` (50) and `2026-10-16-stripe-fresh-repos.json` (381); Shopify `2026-10-16-shopify-repos.json` (50) and `2026-10-16-shopify-fresh-repos.json` (200); AI applications `2026-10-21-openai-app-repos.json` (100) and `2026-10-21-anthropic-app-repos.json` (38, after removing 12 copies of leaked proprietary source), selected by `scripts/ai-app-select.mjs`. Both setup scripts and `benchmark:shopify` take `--list <frozen.json>`. The Stripe benchmark scans serially in one process (`--concurrency` only overlaps validation), so split a large list across processes with `--offset` and `--limit` to finish faster.
- Stripe's published OpenAPI documents are pinned by `stripe/openapi` tag in `docs/benchmarks/2026-10-14-stripe-repos.json`. A local Stripe lab for end-to-end checks lives at `~/Repos/refit-stripe-lab`; it uses simulated responses only.
- Open owner decision: `--full-diff` on real Stripe upgrades reports thousands of enum additions and reachable required-property removals, which block automation. The enum part was relaxed on explicit instruction in the self-maintaining pipeline PR: Stripe response enum additions block only where the code switches over the field. That change needs owner sign-off. Removals inside unexpanded Stripe objects stopped blocking with owner sign-off in 0.25.0. Every other response property change with a named path inside an unexpanded object (any-of additions, became-nullable or optional, max-length and type changes) stopped blocking with owner sign-off on 2026-10-16 (#84). Direct removals the code never reads still block; do not relax the rest of the gate without an explicit decision.
- Yarn 1 root projects are prepared like npm and pnpm; the shared tool installer is `pipeline/manager-install.ts`. `REFIT_DEPENDENCY_TIMEOUT_SECONDS` (60–1800) extends the install deadline. Preparation runs with a 2 GiB workspace and 3 GiB memory (owner decision, 0.28.0); validation defaults to a 2 GiB workspace, 3 GiB memory and 1 GiB archive (owner decision, 0.33.0), always offline; `REFIT_VALIDATION_WORKSPACE=1g|512m` selects smaller profiles; `4g` is an opt-in operator choice (4 GiB workspace, 5 GiB memory, 2 GiB archive, for preparation and validation alike).
- The agent catalog lives in `pipeline/agent-catalog.ts`. Add a provider there with `adapter: null` until a reviewed adapter and rules exist; only entries with an adapter are suggested or addable.
- The API deadline registry lives in `data/deadlines.json`. Every entry needs its provider page as `source` and the day it was checked as `checkedAt`; run `npm run deadlines:check` after editing. `refit serve --deadline-alerts` is off by default and needs the App's Issues write permission; each installation's owner accepts it. `refit deadlines --fail-within` exits 2 for CI. Its exceptions in `.refit-deadlines-ignore.json` must keep requiring a reason and an expiry within a year, and must reject the whole file on any error. Do not loosen these checks without an explicit decision. See `docs/DEADLINES.md`.
- Matches outside application code (owner decision 22, raised on #198; Furqan confirmed it on 2026-10-22 together with the labelling and opt-out): a live deadline match on a docs-site, example, test-fixture or build-output path (`OUTSIDE_APPLICATION_CODE` in `pipeline/workspace-attribution.ts`) counts everywhere, as an exposure, for `--fail-within`, alerts and the model-fix lists, because such paths are often deployed (embedbase's `docs/` calls OpenAI live). `refit deadlines` and `refit report` label it "outside application code" with the reason; nothing is excluded by path name. A repository opts specific paths out only through a committed `.refit-ignore-paths.json` (path globs, each with a required reason); those matches are listed as ignored by repository config and not counted, and a malformed file stops the scan. Do not stop counting these paths, or make the opt-out implicit, without a new decision. See `docs/DEADLINES.md`.
- AI patches default to `gpt-5.6-luna` (OpenAI has no `gpt-5.6-mini`); the price table in `pipeline/ai-budget.ts` accepts dated snapshots. Run benchmarks from a pinned `git worktree`, never the working tree: each `refit run` subprocess loads current source files. `node scripts/stripe-benchmark-setup.mjs --held-out` rebuilds the frozen 50-repository set; `scripts/stripe-benchmark-compare.mjs` compares runs.
- A traced SDK call that still sends a request parameter the target contract removed stops for review (`pipeline/request-removals.ts`). Owner decision (2026-10-16, revised the same day; see `docs/STRIPE-PAYMENT-METHOD-TYPES.md`): Stripe endive's removed `payment_method_types` is replaced automatically only when the value is exactly the literal `['card']` on Checkout Session, PaymentIntent or SetupIntent creation. It becomes `allowed_payment_method_types: ['card']`, only together with the endive `apiVersion` bump and, for TypeScript, the stripe-node upgrade in the same patch. Every other value (card plus other methods, `card_present`, computed lists) keeps stopping for review, and Refit never drops the parameter. Do not widen this without a new decision. Owner decision (2026-10-21): a repository may opt in with `"stripePaymentMethodTypes": "keep-listed"` in `.refit.json`, which moves a literal list of distinct methods that includes `card` (not `card_present`) to `allowed_payment_method_types` with the same methods, under every other case A gate; the draft names each non-card method. Lists without `card`, computed lists and spreads keep stopping. Owner decision (2026-10-16, #88): with `--publish-unresolved` only, a deterministic patch whose sole blocker is a removed request parameter, or whose checks could not run because of the repository's own dependency setup, may be published as a `[Needs review]` draft. The draft leaves the parameter in place and says what to check. AI patches, regressions and any second blocker never get this waiver. Owner decision (2026-10-21): untraced reads of removed field names (same-named reads Refit could not trace to a provider object) count as unresolved, so a draft with them is titled `[Needs review]` and publishes only with `--publish-unresolved`, listing each read as left unchanged; its checks must still pass.
- Signed-webhook payload reads of moved Stripe fields go through the generated helpers in `pipeline/stripe-subscription-periods.ts`, which return the old field when the payload has it and the new location otherwise, so the handler works on events of either version; those reads count as migrated. Webhook reads no helper covers keep stopping through the incoming-version gate, and webhook reads are never rewritten to the new shape only. Owner decision (2026-10-24, overnight sign-off "on everything that will improve Refit towards being an automated API fixer", lane F5, #278): a webhook payload read of `invoice.subscription` goes through `getInvoiceSubscription` even when other code expands `subscription`, because Stripe sends event objects "always in their minimal form" (https://docs.stripe.com/expand, read 2026-10-24). SDK reads keep the expand check. Evidence: refit-bench runs 40077373087 (before, d37db50) and 40083004053 (after, 0de24bf), all 597 tuned repositories, 0 outcome changes, helper-migrated webhook reads 136 to 150 of 191; the one altered diff (brunobola-portfolio/GitHub-Repo-Manager) is reviewed in `docs/benchmarks/fix-reviews.json`, see `docs/overnight/F5.md`. Do not widen this to SDK reads without a new decision.
- Meta Graph API has no agent (`adapter: null`). `refit meta-graph` (`pipeline/meta-graph-calls.ts`) is review-only request detection; `data/meta-business-sdk-edges.json` is generated by `scripts/meta-business-sdk-edges.mjs` from a downloaded, never-installed SDK tarball. `scripts/meta-graph-benchmark.mjs` scores it against `docs/benchmarks/2026-10-20-meta-graph-call-labels.json`. The per-version change list `data/meta-graph-changes.json` takes entries only from developers.facebook.com changelog pages someone read, each with `source` and `checkedAt`; run `npm run meta-graph:check` after editing, and never add a change from a search summary or memory. v14.0 to v26.0 are reviewed from the Graph API changelog pages; the WhatsApp Business Platform and Messenger Platform changelogs are not, so their requests must keep stopping until someone reviews those changelogs too. `refit meta-graph --propose-version-moves` (`pipeline/meta-graph-moves.ts`) is review only: do not wire it into `refit run`, validation or drafts, or relax its stop conditions, without an owner decision on whether the hand-kept list is enough evidence. See `docs/META-GRAPH.md`.
- PayPal has no agent (`adapter: null`). `refit paypal` (`pipeline/paypal-calls.ts`) is review-only request detection for `@paypal/checkout-server-sdk` request classes, `@paypal/paypal-server-sdk` controller calls and raw REST calls. `data/paypal-requests.json` is generated by `scripts/paypal-requests.mjs` from downloaded, never-installed npm tarballs and a pinned `paypal/paypal-rest-api-specifications` checkout; regenerate it rather than editing it. `developer.paypal.com` was unreachable from the cloud environment on 2026-10-21, so PayPal has no deadline entries: add one only from a PayPal page someone read, with `source` and `checkedAt`. Replacing the deprecated old SDK with the new one is an owner decision and stays review-only. See `docs/PAYPAL.md`.
- Retiring AI models (owner decision, 2026-10-20, #120): `refit serve --model-fixes`, off by default, applies the deadline registry's `replacement` as-is in enrolled repositories, validates it with the approved `.refit.json` checks in offline Docker and opens a draft PR without asking per change. It never merges; uses the rule stops on (sampling parameters, spreads, shared constants, tests) stay for review. Do not widen which uses are replaced without a new decision.
- Language tracers (owner decision, 2026-10-22): tree-sitter WASM, the shared `SdkCallRecord` and vendored grammars are the standard path for every tracer outside JavaScript and TypeScript (Python and Go today). Each one goes through `pipeline/tree-sitter.ts`, and `docs/ARCHITECTURE.md` ("Rules every tracer must satisfy") lists what that requires:
  - every grammar is pinned by SHA-256 (WASM and `src/grammar.json`) with its provenance, and is refused on mismatch;
  - per-file size, parse-time, node-count and depth limits are named stops;
  - one language's failure is a stop, never the end of `scanDeadlines` or the model-fix proposal;
  - these languages are report only (`REPORT_ONLY_LANGUAGES`; `proposeModelReplacements` throws on an edit outside JS/TS);
  - `pipeline/tracer-conformance.test.ts` runs on every grammar.
    Do not relax a limit, skip the integrity check, or let a non-JS/TS tracer produce edits without a new recorded owner decision.
- Gemini has no agent (`adapter: null`) and is report only: `refit deadlines --propose-model-fixes` and `refit serve --model-fixes` never edit Gemini code (pinned by a test in `pipeline/model-retirements.test.ts`); widening replacements to Gemini and the `@google/generative-ai` → `@google/genai` swap are owner decisions. The registry's only Gemini entry is that package's end of support (`kind: "sdk"`). Gemini model dates come only from Google's deprecations page on ai.google.dev, which was unreachable on 2026-10-21; never add one from memory or a search summary. See the Gemini section of `docs/PROVIDER-GOALS.md`.
- Indirect model sources (2026-10-21): the model-replacement rule in `pipeline/model-retirements.ts` traces class fields, `const` object members, computed initializers (env fallbacks, conditionals, returned literals, destructuring defaults, options-object parameters) and axios request configs to the literal a request sends, but by default it edits only what it edited before: literals, `??` and `||` defaults, constants and enum members used once, and helper parameter defaults and callers' literals. Every other reached site stops with where its model comes from. Editing them (D-06 to D-08, `{ indirect: true }`) takes the owner decision recorded with that change; shared constants, members, fields and helpers (D-09) stay stops. Every traced OpenAI or Anthropic call outside text generation, any custom endpoint (a base URL, `withOptions(` or `AzureOpenAI` in a source or `.env*`, JSON or YAML config), a module loaded by `import()`, `require()`, a glob, `export *` or an opaque namespace, class inheritance the tracer cannot resolve, an enum, class or object read as a whole or written to, and a trace cut by the depth limit or work budget stop with a named reason. Over-stopping is intended; a wrong edit is not acceptable. Do not widen which uses are replaced without a new decision.
- Sourced parameter stops (2026-10-21; off by default per owner decision, 2026-10-22): only `refit deadlines --propose-model-fixes --parameters <path>` uses the table; `refit serve --model-fixes` and the default command keep the heuristic stops. `data/model-parameters.json`, checked by `pipeline/model-parameters.ts`, records what an official OpenAI or Anthropic page says a replacement model accepts. For a replacement WITH a table entry, the table decides each parameter: the rule continues only where the entry for the final replacement accepts that parameter with a numeric literal written in the request; constants, shorthand, strings, expressions and computed property names stop, and a renamed parameter stops and is never rewritten. On shipped data only a literal `temperature: 1` on a `claude-sonnet-5-5` replacement continues; every other parameter on a tabled replacement stops (`top_p` and `top_k` on Claude Sonnet 5.5, because the official pages conflict and the stricter one governs, or because none states support). For a replacement WITHOUT an entry the pre-existing heuristic is unchanged: Claude 4.7-and-later replacements, such as Opus 4.8, stop on temperature, top_p and top_k; earlier ones, such as `claude-haiku-4-5-20251001`, continue; every OpenAI replacement stops on its sensitive sampling and length parameters, because no OpenAI page states support. A computed property name stops in both paths. Renamed parameters apply to OpenAI only: `o3` `max_tokens` stops with a reason naming `max_completion_tokens`. GPT-6 replacements have no entry, because their acceptance depends on `reasoning_effort`. Entries come only from official pages someone read, each with one `source` and `checkedAt`, never from search summaries or memory; run `npm run model-parameters:check` after editing. Do not widen without a new decision.
- Shopify is a built-in provider: `pipeline/shopify-*.ts`. Its contracts are GraphQL introspection snapshots (`refit shopify-snapshot`), not OpenAPI; `runPipeline` hands them to `runShopifyPipeline`, whose report fills every report field (OpenAPI-only ones empty). The only automatic edit is moving pins when every document validates on the target; an enum pin also needs the locked SDK to define the member (`SHOPIFY_API_ENUM_SINCE`). The frozen benchmark is `docs/benchmarks/2026-10-16-shopify-repos.json`; the lab is `~/Repos/refit-shopify-lab` (simulated responses only; its tests replace the SDK fetch with `setAbstractFetchFunc`).

# Refit agent guide

## What Refit is building

Refit connects upstream API changes to the customer code that may need updating. The product goal is to monitor API contracts and selected documentation, find affected SDK usage, propose a migration, run the repository's checks in isolation, and open a human-reviewed draft pull request as Refit Agent.

Build toward a reliable agent for many API providers, with separate integrations and reviewable changes. Breaking changes are the first priority. Record other changes for review rather than generating speculative code updates. Prefer deterministic, explicitly configured migration rules; use AI only as a bounded assistant behind the existing evidence, budget, validation, and review gates.

## Product boundaries

- Read [READINESS.md](docs/READINESS.md) before describing support or choosing a feature. It records verified behavior and known gaps.
- Refit currently analyzes supported TypeScript and JavaScript SDK patterns. Provider support depends on observed SDK mappings and migration rules; OpenAPI compatibility alone does not mean a provider is ready for automatic fixes.
- Automatic edits must be limited to supported, evidence-backed migrations. Ambiguous code, API versions, request/response semantics, or webhook policies must stop for review.
- Validate changes in the existing isolated workflow. A passing command is evidence about that command, not proof of complete API or code coverage.
- App installation does not activate arbitrary repositories. Configuration and approval are explicit; workers, AI, and draft publication have separate settings. Refit never auto-merges.
- Keep credentials out of repository files and browser code. Never run a live vendor operation or paid model evaluation unless the task explicitly authorizes it and the configured budget allows it.

## Repository workflow

- Read the code and relevant tests before changing behavior. Follow existing architecture and keep changes focused.
- Preserve honest evidence boundaries in CLI output, reports, documentation, and pull requests. Do not claim a simulated test exercised a live provider.
- Run `npm test` after JavaScript or TypeScript changes, and run the relevant typecheck, formatting, and build checks for the touched code. Report what actually passed.
- Use conventional commit messages when committing requested project changes. Do not add co-author trailers.
- Update the relevant user-facing guide and readiness checkpoint when a feature changes supported behavior. Keep the root README short; put detailed setup and limitations in `docs/`.

## Hosted worker (Fly.io + Supabase)

The single-tenant hosted worker (`refit hosted serve`) runs as Fly app `refit-hosted` (region `iad`, one machine, 20 GB volume `refit_data` at `/data`) against the `refit-hosted` Supabase project (us-east-1). The deploy steps, the database role and day-to-day operation are in [Hosted onboarding](docs/HOSTED-ONBOARDING.md#deploy-on-flyio).

- Access: a teammate needs membership in the Fly organization that owns `refit-hosted` and in the Supabase organization that owns the project. Ask the owner for both; do not create new apps, projects or volumes to work around missing access. Run `fly auth login` yourself; agents never type credentials.
- Secrets live only in `fly secrets` (names: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `REFIT_WEBHOOK_SECRET`, `REFIT_SERVICE_TOKEN`, `REFIT_DATABASE_URL`, `REFIT_HOSTED_OWNER`, `OPENAI_API_KEY`, `OPENAI_MODEL`) and in the owner's private `~/.refit/hosted/` files. `fly secrets list` shows names and digests only. Never print, commit or paste secret values, the Supabase project ref or database passwords into this repository, which is intended to become public. Stage a value from a file or variable (`fly secrets set NAME="$(cat file)"`), never from a placeholder: a literal `<value>` is accepted and crashes the worker on boot.
- The worker connects as the `refit_hosted` role, which owns the `refit_*` tables. Do not switch it to `postgres` or the Supabase service key, add RLS policies or expose the tables through the Data API.
- Read-only checks are always safe: `curl https://refit-hosted.fly.dev/health`, `/status` with the service token, `fly status` and `fly logs -a refit-hosted`. `fly deploy`, `fly secrets set`, schema changes, `refit hosted approve` and `refit hosted retry` change the live service; with `--ai-patch` a job spends the owner's OpenAI budget and with `--publish-draft` it can open draft PRs. Do them only when the task asks.
- Hosted mode enrolls only `REFIT_HOSTED_OWNER`'s installations, and only repositories with a stored approval. Widening that to other accounts needs per-job isolation and an owner decision.

## Working in parallel

Several agents build and benchmark at once. To keep out of each other's way:

- One branch and one `git worktree` per task (`git worktree add -b feat/<name> ../Refit-<name> origin/main`). Never edit another agent's worktree or switch its branch. Run `npm ci` in a new worktree before tests.
- Every benchmark runs on GitHub Actions in `refit-dev/refit-bench` ([GitHub benchmarks](docs/GITHUB-BENCHMARKS.md)), not AWS (owner decision, 2026-10-26): Stripe with `benchmark.yml`, Shopify with `shopify.yml`. Dispatch with a full pushed commit SHA and record the GitHub run id with the outcome. Its logs and artifacts are public, so never pass a key in an input; `-f ai=true -f ai_budget=<USD>` uses the owner's capped `OPENAI_API_KEY` secret and spends the OpenAI budget, so do it only when the task authorizes AI.
- Benchmarks simulate production, the hosted Fly worker, as fairly as they can; the remaining differences are listed in [How this matches production](docs/GITHUB-BENCHMARKS.md#how-this-matches-production). When a production setting that changes outcomes moves (`fly.toml`, `Dockerfile`), move the benchmark with it or record the difference there.
- Only when the owner asks for an AWS run: use `node scripts/aws-benchmark.mjs` (profile `refit`, region `us-east-2`; the owner signs in with `aws login`, agents never handle credentials). Use a unique `--run <benchmark>-<date>-<agent>` id, pin `--commit`, keep `--hours` as low as the run needs, and always `collect` or `stop` the run when done. `launch` counts every agent's running shards against the account's vCPU quota and refuses to exceed it; wait rather than raising quotas or limits yourself.
- The AWS project has a monthly spend limit (see Billing) and is on the free plan (on-demand only). Ask before a run that needs more than the free on-demand quota (16 vCPUs, two `c7i.2xlarge`) or more than three hours, and before any `--ai` run, which also spends the OpenAI budget.
- Record benchmark outcomes in `docs/BENCHMARKS.md` with the run id, commit and command, as for local runs.

- Structurally equivalent changes (owner decision D4, Pierce, 2026-10-27): an oasdiff change whose old and new schema accept the same values is not breaking, for any OpenAPI provider (`pipeline/schema-equivalence.ts`). They are listed as `compatible` with their reason; a `currency` value a traced call visibly sends that Stripe rejects stays reached. Each class and its evidence is in `docs/SCHEMA-EQUIVALENCE.md`.

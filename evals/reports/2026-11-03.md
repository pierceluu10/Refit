Six graded units, all from two repos (`4lbatr0s/jiro` and `crlny/lobe-chat`, each set's first
repo), are far too few for a rate to mean anything. Read them as six worked examples.

- **No task could be verified.** Both repos' checks fail before any edit: jiro's typecheck fails
  6 ways and its build once, and lobe-chat's typecheck, build and tests each fail once.
  `verified` needs a check that passes after the change, so every attempt here was
  `needs-review` whatever the edit's quality. On jiro the cause is visible: its `postinstall`
  runs `prisma generate`, which never runs with install scripts off, so the Prisma client is
  missing and the typecheck cannot pass.
- **Every started repo had at least one task.** The match agent called no repo not affected, so
  there is no not-affected unit to grade. Across the 8 started repos it judged 301 change and
  repo pairs: 39 became tasks and 262 got a not-affected verdict with a reason, and none came
  back without a verdict (each result file's `matchReasoning` has them).
- **Attempted is 100%.** Before this branch, each of the 33 tasks the cap stopped would have
  been graded as an attempt bug: since #469 `runTask` returns an empty `failed` record when less
  than `MIN_TASK_USD` ($2) of the run is free. They are now unrun, with the free amount in
  `unrunReason`.

**The AI reviewer matched my merge call on 2 of 6.** It said has-concerns on 5 PRs and
looks-right on 1, about $0.04 each.

- It saw only the diff, never those files. Since these runs, the reviewer also reads the files

  at 40,000 characters).
- On lobe-chat its concerns were real but mostly not blocking: saved settings that still name a

- It turned the jiro pin from looks-right to has-concerns. Its call now matches my merge call on

- Each review cost $0.03 to $0.08 on jiro and $0.11 to $0.12 on lobe-chat, whose model-list files

- After that I added one paragraph to the reviewer's prompt (`reviewer-v2`). It tells the model

## What failed, and why

1. **The cap bought one repo's tasks per set, and stopped tasks that would have fit.** A task
   starts only with `MIN_TASK_USD` ($2) of the run free, because the harness keeps a $1 reserve
   for an Agent SDK turn that overshoots. The six tasks cost at most $0.47 each, yet each set's
   fourth task was refused with $1.48 and $1.60 free. In total 33 matched tasks went unrun, and
   most of each run's last $1.50 went on repos that could only be inventoried and matched.
2. **Every baseline was already red,** so verified was out of reach (see Results). This says
   nothing about the edits. It says the sandbox can't build these repos as they stand, partly
   because codegen that lives in `postinstall` never runs with install scripts off.
3. **The match agent split one upgrade into four tasks.** Its four jiro tasks were all facets of
   one move, stripe-node 14 to 23, which is Endive. The harness then opened three PRs that
   overlap and partly conflict; only one is worth merging. The three stripe repos got 3, 4 and 6
   tasks, several of them conditional ("nothing breaks until the SDK is upgraded") or years out
   (Node 22 support ends in 2028). lobe-chat's 12 tasks were distinct model retirements, which
   is the right shape.
4. **The watcher reads the newest changes, and these repos are years behind.** The Stripe
   watcher returned 42 changes from Dahlia, Endive and stripe-node v23. jiro's upgrade also
   needed Basil's move of `current_period_end` (2025-03-31). The harness found that from the
   SDK's types; no change named it.
5. **The reviewer guessed at code it could not see,** and didn't know a parameter newer than its
   training data. The first is fixed: it now reads the files, and the re-review shows the
   guesses gone. For the second, it now says what it couldn't confirm instead of calling it
   invented, but it still can't check it.
6. **The Actions benchmark could not have run a task (found while planning the next run).**
   `matrix` split the whole cap evenly, so the suggested $40 across 30 shards gave each $1.33,
   below the $2 a task needs. Each shard, a fresh process, would also have paid its own watcher
   read: $0.40 to $0.89 here, 30 times over. Fixed in this branch:
   - a `watch` job reads each provider once and hands its cache to every shard;
   - `matrix` takes that job's `WATCH_USD` per provider out of the cap first;
   - `matrix` refuses a cap that leaves a shard under $2.

## What I'd do next

- **Harness (O5): let a task start with less than $2 free.** For example, size the minimum to the
  run's observed task cost plus the overshoot reserve, or let the harness start and stop at its
  reserve. At this run's costs, each set's last $1.50 would have run two or three more tasks.
- **Harness (O5): get green baselines.** Have the agent run the repo's codegen inside the
  sandbox before the baseline (`prisma generate` and the like), or record which baseline
  failures are environmental, so `verified` becomes reachable.
- **Match agent (O4), as prompt guidance rather than a rule:** when one SDK or API-version
  upgrade resolves several changes, make one task for the upgrade and name the rest in it.
- **The next benchmark:** fix the first two, then run each set with a cap that reaches past the
  first repo. At this run's means ($0.40 per repo for inventory and match, $0.43 per task with
  its review, 4.9 tasks per started repo), 10 repos would need roughly $25. That is arithmetic
  on the means above, not a measurement.
- **Evals:** run `longtail-dev-20`, the Anthropic set and the Gemini set once F4's
  `anyProviderWatcher` is wired (the `watchAny` line in `runner/cli.ts`). Give the reviewer the
  change's source page as well as the files, so it stops calling parameters newer than its
  training data invented.

## Design choices

**One helper per moved field, legacy first.** For a field with a one-to-one replacement, the generated helper reads the old field through `Reflect.get` and returns it when the payload has it, otherwise the new location. An old-version event, a new-version event and an event replayed from before the endpoint moved all give the old code's result. The gated SDK test (`REFIT_STRIPE_SDK=1`, stripe 17.7.0 and 19.1.0, simulated events signed locally) now delivers both shapes to the helper-patched fixture handler and checks the same result for both. A subscription whose items have different periods keeps the original missing-period error, because the handler has no plan selection.

**Webhook reads skip the expand check (#278).** The `invoice.subscription` helper refuses to rewrite when the code expands `subscription`, because the expand path moved too. That check is repository-wide and also matched an `expand` keyframe in a Tailwind config and an `expand` identifier. Stripe never expands event payloads: "You can’t receive webhook events with properties auto-expanded. Objects sent in events are always in their minimal form" ([docs.stripe.com/expand](https://docs.stripe.com/expand#expansion-with-webhooks), read 2026-10-24). So webhook reads skip it; SDK reads keep it.

**Cast receivers (#279).** `(x as any).field` reads are confirmed by tracing, not by the cast. The rewrite passes the cast through. Under `as any` the result keeps `as any`, because the generic helpers would type it `unknown` and break code that compiled.

**Not built: recognising code that already reads both shapes.** brunobola-portfolio/GitHub-Repo-Manager fills the old fields from the new ones in its own `normaliseStripeEventShape(event)`. cyberdreadx reads `parent?.subscription_details` first and falls back to `subscription_details`. Refit still reports the old-field reads. With the helper they are rewritten harmlessly (the helper returns the same value), but they cannot be told apart from unsafe reads in general. Two repositories do not justify a pattern rule.

## Design questions

**Should Refit tell the customer to move the webhook endpoint's version, and when?** Yes, after the draft is deployed, never before. Stripe's guide ([docs.stripe.com/webhooks/versioning](https://docs.stripe.com/webhooks/versioning), read 2026-10-24) says "Each webhook endpoint has a specific API version. Stripe uses that version to structure the event payloads it sends to the endpoint". Its upgrade path runs a second endpoint at the new version alongside the old one, so for a while every event arrives in both shapes. A handler rewritten to the new shape only would break in that window. The dual-read helpers make the order free: the customer can merge, deploy, and then follow Stripe's guide whenever they like. The draft body (P4's `review.ts`) already says endpoints keep their version until updated. For drafts whose webhook reads all go through helpers, it should add: "the handlers read both shapes, so move the endpoint after this deploys". The page also notes that endpoints can move within one major release without code changes, so that sentence matters only for majors such as basil. Not changed tonight (P4's file); request on the board.

**Is a dual-read helper the right permanent shape, or should a follow-up draft remove the fallback?** Keep it. A cleanup draft would need to know that every endpoint is on the new version. Refit cannot see that from code, and asking Stripe would be a live call. The fallback costs one `Reflect.get` per read. Old events stay in their original shape: Stripe's Event reference says `api_version` is "The Stripe API version used to render `data` when the event was created. The contents of `data` never change" ([docs.stripe.com/api/events/object](https://docs.stripe.com/api/events/object), read 2026-10-24). A replayed, retried or `stripe.events.retrieve`d old event still needs the fallback. Developers do the same by hand (brunobola's normaliser). A cleanup could be offered only after the customer confirms the endpoint moved, which would be a P4 feature, not a default.

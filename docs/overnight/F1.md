### Unresolved same-named reads

From run 40074110257 (P2's zero-spend probe, `main` code, 579 of 597 rows): `.price` is the largest unresolved read (1,368 review findings, 658 distinct sites in 163 repositories), and in **67 repositories `price` is the only review finding**, so it alone makes their drafts `[Needs review]` (F4 found the same). Reading all 658 lines:

- `PLANS.find((plan) => …).price` over a `const PLANS = [{ … }]` the application writes itself (the quill PDF-chat starter family): 39 repositories. Provably not Stripe. **Slice 2.**
- `subscription.items.data[0].price`: 71 reads in 25 repositories. A subscription item keeps `price`; only `line_item.price` and `invoiceitem.price` go. A path rule from the spec could clear these, but it fully clears only 4 of the 67 price-only repositories, so it was not built tonight.
- `const { price } = await req.json()` / `req.body`: about 15 repositories (the Spotify-clone family). The request body is whatever the sender posts, so Refit cannot prove it is not a Stripe object. Left as review on purpose.
- App-owned values from databases and carts (`product.price * 100`, `item.price`): untraced. They need the database client's types, which Refit does not read.

### Slice 2: object literals the application writes are not Stripe objects

`pipeline/source-literals.ts`: an unresolved read whose receiver is an object written as a literal in the application (a `const` bound to an object literal, an element of a `const` array of object literals reached through `find`, `at`, an index, `for…of` or an element callback, or a property of a `const` object literal that is itself one) is not reported. Proving it is not Stripe is as strict as proving it is: a constant whose elements or properties are read must never be assigned into, deleted, pushed to, passed anywhere or placed in another value, and a nested object handed to a variable or an argument counts as changed. Spreads, mutable bindings, mapped copies, reassigned callback parameters and properties that are not themselves literals stay review.

## 3. Design questions

**Is a type-checker trace over the whole program more reliable than syntactic tracing for the remaining causes, and at what cost?**

Not for edits, measured by what the remaining causes are:

- The analyzer already builds one TypeScript program per repository (`analysisProgram` in `pipeline/analyzer.ts`), with `noLib` and without `node_modules`, so it has no Stripe types. A checker trace needs the installed `stripe` types, which exist only after dependency preparation (offline Docker), and the benchmark's scan stage never installs. `pipeline/stripe-type-evidence.ts` already does exactly this when a package directory is available, capped at 2,000 files because one full program can exhaust the heap (`SimplerDevelopment/SimplerDevelopment` needed `--max-old-space-size=6144` and 521 s even for the syntactic scan).
- The remaining causes are where types lie. Every lazy Proxy is `new Proxy({} as Stripe, …)`: a checker says "Stripe" for the empty object before any trap runs. Injected parameters (`deps.stripe: Stripe`) and class fields are typed by annotation, not by origin. A cast is exactly what the owner decisions treat as unproven (`typeEvidence` findings stop migration for review).
- So the checker is the right tool for **review evidence** (it already finds reads the syntactic tracer cannot), and syntactic origin tracing stays the gate for **edits**. The cost of a whole-program check is a prepared install plus seconds to minutes per repository; the syntactic scan is under a second for most repositories.

**Where should tracing give up, and how does the customer see it?**

- It should give up exactly where origin cannot be proven: a client passed into an exported function, a client read from a container or cache keyed at runtime, a bare `stripe` import under a configuration whose `extends` Refit cannot read, and a value that arrives over HTTP. Each of these is a named stop or a review finding today, never an edit.
- The customer sees it in the draft or the stop: an untraced call is invisible (the real gap), so the most useful next step is to **report** untraced likely Stripe calls per file (the coverage tool already finds them by shape), so "not affected" can say "and N calls Refit could not follow, in these files". P3's #272 already names the tsconfig `extends` Refit does not read.

## 4. Decisions taken under the bar

None. Both slices change what Refit sees, not what it edits: slice 1 traces more calls through the existing gates, slice 2 removes review findings on values that cannot be Stripe objects. Neither turns a review-only rule into an automatic edit.

## 5. What is left, ranked

1. **Unreadable tsconfig `extends`** (24 repositories). Resolve workspace-package `extends` from the repository's own `package.json` names (provable, 4 repositories), and published bases by reading the pinned package files (`astro/tsconfigs/*`, `@tsconfig/*`, `expo/tsconfig.base` set no `paths` or `baseUrl` at the versions to check). Generated `.nuxt/` and `.svelte-kit/` configurations need the framework's alias rules and the app's `nuxt.config` aliases; until then they stay unknown.
2. **Subscription item path rule** for `.items.data[n].price` (25 repositories, 71 reads), from the specs: every Stripe schema a `.items.data[n]` path can reach must keep the field.
3. **Exported helpers taking the client** (about 15 repositories): trace when every caller in the repository passes the same client and the helper is not reachable from outside (not a package entry point).
4. **Destructured resources** (`const { customers } = stripe`), with the same immutability checks as aliases.
5. Keep going items: JavaScript-only repositories (untyped clients, O4's causes 3, 6 and 7), and monorepo packages that wrap the client.

1. Prefer a repository that already has a `refit-dev` fork.

3. Then take the list order.

## Design questions

Fly prices are from [docs.fly.io/about/pricing](https://docs.fly.io/about/pricing), read at 08:10Z (iad): shared-cpu-2x with 2 GB is $13.39/month, RAM beyond a preset's is $6.00/GB/month, performance-2x with 4 GB is $66.00/month, and volumes are $0.15/GB/month. Stop-signal behaviour is from the [Fly configuration reference](https://docs.fly.io/reference/configuration).

### Is one machine per job needed before a first customer?

Yes, before a second GitHub account's repositories run on this worker. No, for the owner's own repositories.

- **The shared worker's boundary is Docker.** Validation runs the repository's own commands, which are arbitrary code, in offline Docker on the worker VM. That VM's worker process holds `GITHUB_APP_PRIVATE_KEY`, `OPENAI_API_KEY` and `REFIT_DATABASE_URL`. If a customer's tests escape their container, they can read the App key and mint tokens for every installation, and they can read the database URL, which holds every customer's rows.
- **The isolation is already built.** The job-machine path (`pipeline/fly-machines.ts`, `runHostedTarget` on a machine) runs each job on its own Fly machine with only a read token for its repository. The parent keeps publication (`hosted-runner.test.ts`, "runs a job on its own machine with only a read token"). It has never run on Fly. It needs a Fly API token secret and an owner decision to switch it on, and neither was in this lane's permissions tonight.
- **Cost.** Per-job machines bill per second. A 182-second job on performance-2x costs about $0.005 at $66.00/month. Machine start time adds to every job and was not measured tonight.
- This agrees with AGENTS.md: widening enrollment beyond `REFIT_HOSTED_OWNER` needs per-job isolation and an owner decision.

### What is the cost per job and per installation per month?

- **Fixed cost.** shared-cpu-2x with 4 GB is $13.39 + 2 × $6.00 = $25.39/month, as in `docs/CAPACITY.md`. The 20 GB volume adds $3.00/month, for $28.39/month in all. Supabase is not included, because its plan page was not read tonight.
- **Per job.** On a per-job performance-2x machine ($66.00 / 730 h = $0.090/h):
  - a full QueryPDF run (182 s) costs about $0.0046;
  - a cached poll (3 to 7 s) costs about $0.0002.
  - On the always-on worker the marginal cost is zero. What limits it is capacity: the shared-cpu-2x quota is 0.125 of a core, and re-polling 8 repositories every 5 minutes already used it up (2 min 53 s of every 7-minute round).
- **Per installation.** A 300-second interval is 8,640 polls per target per month.
  - On main, every poll re-runs the cached path, at 4 to 64 s each on shared-cpu-2x.
  - With #252, an unchanged target's poll only reads the database. A new base commit or a new contract still gets a full run.
  - So per repository the cost is about $0.0046 × (base commits + contract changes) per month on performance-2x job machines, plus AI.
- **AI.** $0 tonight. No hosted job reached the model: `refit_ai_ledgers` and `refit_ai_total_ledger` are empty. Each installation is capped at `REFIT_AI_BUDGET_USD` ($2).

### What should the 120 s check limit be on hosted hardware?

Keep 120 s, as a limit for one unthrottled vCPU, and do not run validation on a throttled shared vCPU.

- **Headroom on performance-2x.** QueryPDF's checks took 24.0 s (baseline) and 29.5 s (patched), four times under the limit.
- **On a throttled shared-cpu-2x, 120 s is not enough.** Every stage before validation took about 7 times longer (84 s against 12 s). At that rate the same checks would take roughly 170 to 210 s and stop as `Check exceeded 120 seconds`. The result reads as the repository's failure when the cause is the hardware.
  - The 300 s dependency limit has the same problem. Job 254 hit it on install, which took 57 s on performance-2x.
  - Raising either limit on throttled hardware would only make each job hold the worker longer.
- **Where to run validation.** Use per-job performance machines, or scale up while full runs are queued.
- **#252 keeps the shared machine usable.** It stops idle polls from draining the burst balance, so occasional full runs on the shared machine get burst CPU.
- **Not measured.** No test-suite repository was timed (QueryPDF runs a typecheck). The draft-created forks were not re-run, to avoid duplicate drafts before P4's #251.

### What happens to a running job during a deploy, and should deploys drain first?

Yes, deploys should drain first.

- **On main `fc4dc00`.** Fly sends `SIGINT` and, after `kill_timeout` (5 s by default), `SIGTERM`. The worker aborts the running job.
  - When the abort lands inside the workflow, the job is stored `finished`/`error` with a generic message.
  - Later polls reuse that result until an operator retries (`watch.ts` reuses `error` unless retry is set).
  - So a deploy during validation silently parks the target, and nobody is alerted.
- **With #256.**
  - `refit hosted pause` stops claims in every worker (migration 11), and `/status` shows whether a job is still running.
  - The first stop signal drains: the running job finishes and nothing new starts.
  - `kill_timeout = 300`, Fly's maximum, gives the running job up to 5 minutes. A second signal, Fly's `SIGTERM` after 300 s, interrupts it.
- **With #258.** An interrupted job is stored as `interrupted`, logged as an error and reported by the failed-job notice.
- **Runbook order.** Pause, wait until no job is running, deploy, then resume. A job longer than 300 s cannot finish inside one kill timeout, which is why the pause comes first.

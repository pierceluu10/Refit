## Forks

The forks are 30 new repositories plus the 8 already enrolled, 38 in all. The list is [`docs/benchmarks/subsets/p1-forks.json`](../benchmarks/subsets/p1-forks.json).

**Selection rule.** The candidates are the affected rows of the four tuned sets (active, fresh, original, held-out), never the night set. Each repository falls into one outcome class from its latest committed benchmark result. Within each class:

1. Prefer a repository that already has a `refit-dev` fork.
2. Then prefer the active set, then fresh, then original, then held-out.
3. Then take the list order.

The 8 enrolled forks are excluded from the 30. Twelve of the 30 already had forks. The other 18 were forked into `refit-dev` at 07:30Z.

**Pinned commit.** Each fork has a `refit-base` branch at the pinned benchmark commit, created from the frozen list's `commit`. The hosted target's base is `refit-base`.

**Infrastructure failures.** Nineteen of the 38 failed with an infrastructure error:

```text

```

The `refit-bench` workflow pulls only `node:22-alpine`, never the image the generated checks use. P2 reported this to O5 on the board.

For those rows, the benchmark outcome is unknown until the workflow pulls the image.

**Zero-config path at fc4dc00.** The customer path with no hand edits fails on every new fork. A fork without a committed `.refit.json` cannot be enrolled:

```text
refit enroll: Repository profile input is not a committed regular file: .refit.json
```

So all 30 new forks are predicted "not enrolled". The 8 enrolled forks keep their operator-written configurations and cached results.

**Production mode.** With a configuration in place, the hosted worker scans with `fullDiff` on. That is the default in `watch.ts` and `readiness.ts`, and the customer proposal sets nothing else.

Every one of the 38 has at least one operation impact under production mode (column "Impacts"). So, on fc4dc00, a customer configuration stops for review at the scan, before validation, wherever doctor passes.

**When the predictions get redone.** The predictions are redone at the commit that is actually deployed. That happens once P3's generated configuration (zero-config enrollment) and O1's operation-impact gate merge, using a benchmark run at that commit.

## Hand edits a fork still needs

These were sent to P3 on the board. On fc4dc00, a customer has to do all of this before `refit enroll` works:

1. Write and commit `.refit.json`. The only proposal is the one in the hosted approval issue, and it is incomplete:
   - It has no `apiVersion`.
   - Its check is `npm test`, or `npm run build` when there is no test script. It uses npm even for pnpm and Yarn repositories.
   - It has no generated checks.
2. Make and commit the before and after contracts. The before contract needs the `stripe/openapi` commit for the pinned API version, which nothing maps for the customer. For example:
   - `refit stripe-snapshot --revision <commit> --output refit/stripe-before.json`
   - `refit stripe-snapshot --latest --output refit/stripe-after.json`
3. Leave `fullDiff` unset. Production mode then stops for review on operation impacts (see above).

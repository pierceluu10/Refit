## 3. Slice 1: `payment_method_types` outside a traced body (PR #268)

**The problem.** The removed-parameter check read only a direct object literal passed to a traced SDK call. A body built in a variable and passed in, spread from an exported config, returned by a helper or sent through a client the tracer misses was invisible. The card rule (or any other rule) then moved the pin to endive while that body still sent the parameter, and endive answers 400. On main, `brendansudol/punchlines-ai` (pin 2022-11-15 moved to endive) and `4NDR3S-01/StyleHub` (two renamed sites plus the pin) got such proposed patches. Neither validated, by luck: a regression and a failing baseline.

**The fix.** Each top-level `payment_method_types` key outside a traced SDK body becomes a review finding, and it stops like a traced site. It is not a stop when the key is:
- nested (`payment_settings.payment_method_types` is still valid on subscriptions and invoices);
- given an object value (a schema definition);
- in a test file;
- in a local variable whose every use is a property access or a traced call that still accepts the parameter. endive keeps it on Payment Links.

**Measured.**
- Source scan of the 307 repositories on main and on the branch: 21 change.
- Every new site was read: each is a Checkout Session or PaymentIntent body (variables mutated then passed in, an exported config spread into the call, a helper's `return`, a client the tracer misses, and EliteVault's `[...CHECKOUT_PAYMENT_METHOD_TYPES]` spread).
- 14 of the 21 already stopped on unprovable reads and now also name the site. Seann-Michael/Local-GMB-Booster's helper-only patch (no pin move) now stops, consistent with the existing rule that any removed parameter still sent stops the run.
- Actions, `subsets/f2-untraced-sites.json` (the 21 plus MeiyuTech/AET-App as a Payment Links control), size 1, no AI: before **40079299398** at 92f1137 (main fc4dc00 plus the list), after **40082035846** at 22fb650. `scripts/stripe-benchmark-compare.mjs`: 19 of 22 have the same outcome, and the 3 that change are the ones the scan predicted.
  - `4NDR3S-01/StyleHub`: validation-baseline-failed → needs-review (removed parameter).
  - `brendansudol/punchlines-ai`: validation-regression → needs-review.
  - `Seann-Michael/Local-GMB-Booster`: error → needs-review. On main its baseline and patched checks passed and only the missing stripe-mock image errored, so this is the one repository that was effectively validated before and is not now. Its patch only added the period helper and moved no pin, so it was not wrong. The new stop is the existing policy (a removed parameter still sent stops the run) applied to a site Refit could not see before: `server/routes/payments.ts:48` sends `payment_method_types: ["card"]` to `checkout.sessions.create`.
  - EliteVault and Best-Saas-Kit--V2 keep needs-review, with the removed-parameter reason now coming before the declared-type one. AET-App is unchanged.

**Design choices.**
- A stop, not an edit. Renaming a key in a variable is safe only when the variable provably reaches only the removing call; that would be a widening, and it needs the bar.
- Scoped to `payment_method_types`. The same blind spot exists for `coupon` and `promotion_code`, but those names are common in application code (a store's own coupon objects), so a text-level stop would be noisy. That needs tracing, not a key search: see "What is left".

## 6. Slice 3: the card rule for local request bodies (PR #280, under the bar)

## Owner questions (with numbers)

**Should Refit propose a `[Needs review]` draft that moves the list and asks the customer to confirm, instead of stopping?** Measured: 28 repositories send a literal `card` plus other methods (PayPal in most), and 5 more send a value the rule cannot read. The docs do not prove the move preserves behaviour: the filter adds Dashboard enablement and per-buyer ranking for exactly those methods. So this cannot clear the bar as an automatic edit. The `keep-listed` opt-in already does the move with a per-method warning when a repository asks for it. My recommendation: keep the default stop, and let `--publish-unresolved` (decision #88) publish the `keep-listed` rename as a `[Needs review]` draft that names each non-card method, rather than leaving the parameter in place. Decision needed: Pierce.

Keep stopping; not worth a rule tonight.

## 4. Clients whose version cannot move (slice 2, PR below)

34 card-only repositories stop because a client's `apiVersion` is unknown to the tracer. Reading every one of the 57 unknown constructor declarations and 4 unknown request declarations in them:

| Shape | Example | Can the pin move safely? |
| --- | --- | --- |
| `require('stripe')(key)` or `new Stripe(key)` with no options, on a client the tracer does not follow | ClinkedIn/Backend, Natours-app, basanta1 `module.exports = stripe` | Only through the stripe-node upgrade, and only if every use is known |
| A literal `apiVersion` on an exported client | convex-saas, SatvikPraveen/Nextjs-Ecommerce, geallenboy/ai-saas-template | Not proven: see below |
| A lazy `client ??= new Stripe(…)` getter, or a class field | BurrowSoft/solvymed, buildFast10x/Nextjs-Boilerplate | Not proven |
| A client created inside a handler and reassigned (`stripe = new Stripe(…)`) | Dursun242/Zenbat | Not proven |
| A request whose body is a variable (`customers.update(id, params)`): stripe-node reads a trailing options hash, so a variable body may carry `apiVersion` | SatvikPraveen, mhaowork/warranty-watcher, Bizgojo | No: stays unknown |

**Decision: do not move the pin of a client whose uses the tracer cannot see.** I built it first (6cc80dd). The idea: stripe-node fixes the version at construction, so an escaped client still sends its literal pin, unless the repository calls `setApiVersion`, writes the private `_api`, sends a raw `Stripe-Version` header or spells `apiVersion` outside a checked place. The repository's own tests then showed the flaw (`import * as namespace; configure(namespace)`). The client still sends that version, but its consumers are exactly the code Refit cannot see, including third-party code: the better-auth Stripe plugin receives the client, makes calls and reads fields from inside `node_modules`. Moving the pin changes what that code gets back, with no finding, no edit and nothing validation can catch. So the relaxation was backed out in 901ad49, and the fix belongs in tracing: when F1 traces lazy getters, factories and class fields, those clients become traced and their pins move under the existing gates. That is F1's lazy Proxy and factory work.

What slice 2 keeps:
- **An escape-hatch guard (a correctness fix).** On main, a traced client with a literal pin was "verified" even when the repository also called `stripe.setApiVersion(…)`, wrote `stripe._api`, or set a raw `Stripe-Version` header, so a patch could bump a literal that is later overridden. Any of those now leaves every Stripe constructor's version unknown.
- **The stop says why.** A `payment_method_types` site the card rule could rename, but whose rename is dropped by a gate, now says which one: the client at `file:line` whose version Refit cannot resolve, no literal pin to move, or the stripe-node upgrade's refusal reason (for example "Only root npm, pnpm or Yarn 1 projects with … exactly one of package-lock.json, pnpm-lock.yaml or yarn.lock are upgraded"). With the parameter's existing note (what endive changed, and the decision to make), that is the customer's explanation: pin the client in code, or fix the lockfile, and Refit makes the rename.

## 5. Keep going: `coupon` on promotion codes and subscriptions (with F4)

- **`promotionCodes.create`**: already automatic on main. `stripe-request-moves.ts` (F4) moves `coupon` into `promotion: { type: 'coupon', coupon }`, per the clover polymorphic-coupon page. Nothing to add.
- **`subscriptions.update`**: keeps stopping. The endive [update reference](https://docs.stripe.com/api/subscriptions/update) says a populated `discounts` array "overwrites the existing discounts on the subscription". The old singular `coupon` set one coupon. Whether the subscription had other discounts that the move would delete is account data, not code, so the move is not provable. `REMOVED_PARAMETER_NOTES.coupon` already asks the customer exactly that.
- **`subscriptions.create`**: keeps stopping. The acacia [create reference](https://docs.stripe.com/api/subscriptions/create?api-version=2025-02-24.acacia) says the old `coupon` "will only affect invoices created for that particular subscription", and that `discounts`, when "not specified or empty, inherits the discount from the subscription's customer". Neither page says whether a singular `coupon` also suppressed the inherited customer discount, which `discounts: [{ coupon }]` does. Not settled by the docs, so no rule.
- The same blind spot slice 1 fixed for `payment_method_types` (a body built outside the traced call) exists for `coupon` and `promotion_code`. A key-level stop would be noisy there, because applications use `coupon` in their own objects. The right fix traces request bodies through local variables; it is listed below.

## Design questions, answered

1. **Should Refit propose a `[Needs review]` draft that moves the list and asks the customer to confirm, instead of stopping?** For card plus other methods (28 repositories, plus 5 with unreadable values), it does not clear the bar: Stripe's docs say the filter can hide buyer-dependent methods. My recommendation, as an owner question with the numbers above: under `--publish-unresolved` only, publish the `keep-listed` rename as a `[Needs review]` draft that names each non-card method, instead of a draft that leaves a parameter endive rejects with a 400. A draft that leaves the parameter in place is broken once the pin moves. A draft that moves it is correct unless the merchant relies on a method the filter hides, and the draft can name those methods.
2. **Is `card_present` ever in scope?** A replacement exists in endive (`allowed_payment_method_types` accepts `card_present` and `interac_present` on PaymentIntents and SetupIntents). Equivalence depends on reader and location configuration that offline checks cannot see, and it is 1 repository. Out of scope; it keeps stopping.

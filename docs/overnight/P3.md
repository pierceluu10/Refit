## Assumptions (recorded here and in the PR)

1. **No `node -e 0`.** The benchmark falls back to `node -e 0` when a repository has neither tests nor TypeScript. A generated configuration stops with `no-checks` instead, because such a check shows nothing about the change. O2 owns the check selection; slice 1 takes O2's rule when it lands.
2. **The stripe-node default.** A client without `apiVersion` sends the default of the locked stripe-node release. Stripe says so for stripe-node 12 and later, and that earlier releases send the account's default ([Set a Stripe API version](https://docs.stripe.com/sdks/set-version), read 2026-10-24). Refit knows the last release of each API version (`STRIPE_SDK_RELEASES`, from stripe-node release tags), so the default is the first recorded release at or after the locked one, in the same major only. This is the benchmark's rule plus the same-major guard; a release before 12, in a major the table skips (21) or newer than the table stops instead.
3. **Written literals on unfollowed clients** are used, with the warning in the proposal source, because the constructor option is what stripe-node sends. A request on such a client that overrides the version would be invisible; the review tells the person to check.
4. **`node:22-alpine`**, as the benchmark and hosted forks use.
5. **Contracts live outside the repository**, so a generated configuration needs `refit stripe-snapshot --version` (doctor names the exact command). The hosted worker saves them itself: P1 is wiring `pipeline/hosted-approval.ts` and `service-worker.ts` on top of slice 1.
6. **A generated approval covers one move.** Its fingerprint covers the generated bytes, so it stops for a new approval when the code's API version changes (for example after the customer merges Refit's draft) or when Refit's table gains a newer target. Re-approving each move is the explicit-approval rule; keeping an approval across moves would change what an approval means, so it is left for the owner.

## Design questions

**Enroll with no approval for read-only scans, and approve only before validation or publication?** Yes for the CLI, and it already holds: `refit doctor`, `refit deadlines` and `refit report` read files only and need no approval, and with slice 1 doctor gives a stranger the complete analysis with zero edits. Approval should stay before validation, because validation runs the repository's own install and tests in Docker, and before publication. For the hosted worker, a read-only scan of a repository nobody approved would widen hosted enrollment beyond `REFIT_HOSTED_OWNER`'s approved repositories, which `AGENTS.md` reserves for an owner decision; until then, the approval issue is where a stranger sees the scan.

**Enrollment default `fullDiff: true` (with O1's gate) or `false`?** Keep `true`, the production default, and leave it unset in the generated file so O1's gate applies the moment it merges. Evidence: with `true`, 0 of 35 generated configurations are ready; with `false`, 22 are. But `false` hides what oasdiff reports on the operations the code calls (here, mostly `response-property-became-optional` 2,671 and `response-property-any-of-added` 1,125 across the 25 repositories first measured), and the open owner decision on `--full-diff` in `AGENTS.md` stands. The gap is O1's to close, and the numbers above are for the owner.

**The minimal check for an honest "validated" with no tests?** For a TypeScript repository, `tsc --noEmit` with `compareTypeErrors` (new type errors only) is a real check of a Stripe migration, since stripe-node's types encode the API version; it is what 28 of the 35 got. For plain JavaScript without tests, nothing that runs offline proves a migration: `node -e 0` proves only that dependencies installed, and a syntax check of the changed files proves only that they parse. So slice 1 claims nothing there and stops with `no-checks`, telling the customer to add a test script. O2's generated `stripe-mock` checks (`docs/GENERATED-CHECKS.md`, on `main`) do not change this. They run in addition to `command` and only after it passes, so they cannot stand in for a missing check. They call only simple exported functions, and on the Stripe benchmark none of the 6 deterministically patched repositories ran one to the end: three loaded, then stopped creating a Supabase client. The honest wording stays "not validated". All 14 `no-checks` stops in the 60 and the forks (13 repositories; kaorii-ako/Shiori-v1 is in both) were checked by hand: none has TypeScript declared, and the two with a `test` script use npm's placeholder `echo "Error: no test specified" && exit 1`. **A `build` script is not the answer either**, although 10 of the 13 repositories have one. Each of the 5 Next.js apps imports `next/font/google`, whose "CSS and font files are downloaded at build time" ([Next.js](https://nextjs.org/docs/pages/api-reference/components/font), read 2026-10-24), so their builds need the network the sandbox does not have. The 2 `vite build` apps (CapChris20/Retronix-Wallpapers-Startup, adrianhorning08/web-scraping-course-app) bundle the client only, not the Express server that calls Stripe. `strapi build` builds the admin panel. That leaves `nuxt build` (OpenformStack, which also stops on `source-resolution`) and a workspace build, too few to make a default from.

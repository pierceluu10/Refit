## Design questions

**How should a rule treat a read whose replacement can be absent (nullable in the new shape)?**
- The rule moves the read only when absence already has a meaning the code handles: the old field was itself nullable or optional (`invoice.subscription`, `promotion_code.coupon`, `confirmation_secret` against `payment_intent`). The helper then returns `undefined` (or `null`, as the old field did) and never a default.
- The existing helpers follow this:
  - `getCouponId` returns `undefined` when the typed holder has no coupon;
  - `getInvoicePriceId` returns `undefined` when `pricing.type` is not `price_details`;
  - `movedReadEdit` keeps a `?.` read short-circuiting as `(x == null ? undefined : helper(x))`.
- Where the old field was required and the new one is nullable, the code may rely on presence. That is a behaviour change, and the read stops with the reason. Examples: `product_marketing_feature.name` loses `required`; `invoiceitem.pricing` is nullable.

**When the replacement has several values (`discounts[]`), is "the first" ever provably right?**
- Not from the code alone. A list on a Stripe object can be extended outside the code: in the Dashboard, by another integration, or by a promotion code the customer types in Checkout. So "the code only ever sends one" does not bound what the response holds.
- The one multi-value case Refit automates proves equality instead of picking: the period helper uses the period every item shares, and stops (`flagged`) otherwise.
- So "the first" is never automatic. Each multi-value reason above ends with the question the customer must answer.

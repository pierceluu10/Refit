Lane P4 of [the overnight plan](../../OVERNIGHT-AGENTS.md). Owns `pipeline/review.ts`, `pipeline/publication.ts`, `pipeline/workflow-presentation.ts`, `pipeline/migration-review.ts`, `pipeline/watch.ts`, `pipeline/github*.ts`, `docs/PULL-REQUESTS.md` and `docs/AUTOMATION.md`.

## Slice 1: one draft per target version

### The duplicate on `refit-dev/full-stack-starter-kit`

Two open Refit Agent drafts migrate the same code. The evidence comes from read-only `gh pr view`, `gh api .../git/refs/heads` and `.../compare`:

|                          | PR #1                                                                                         | PR #2                                                                         |
| ------------------------ | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Created                  | 2026-10-16T01:54:51Z                                                                          | 2026-10-24T04:46:19Z                                                          |
| Published by             | the held-out Stripe benchmark (`stripe-benchmark-cli.ts`, `forkAtCommit` then `publishDraft`) | the hosted worker (`pollServiceTarget` → `watchOnce` → `runWorkflow`)         |
| Base                     | `refit-base` at `629b2e4` (the frozen commit)                                                 | `main` at `3da4029`, which adds only `.refit.json` and `refit/*` to `629b2e4` |
| Run id                   | `8627e030…`                                                                                   | the same                                                                      |
| Patch hash               | `ca5961d9…`                                                                                   | `b1b116b9…` (a newer helper template: 110 lines instead of 48)                |
| `refit-migration` marker | `43a6dc04…`                                                                                   | `210e909e…`                                                                   |

Recomputing `migrationIdentity` from a read-only scan of the fork gives exactly both markers. The revision is the only input that differs.

The worker missed PR #1 for three reasons:

1. `findExistingMigration` lists only open drafts whose base is `main` and whose base commit is the scanned revision.
2. Its marker hashes the revision.
3. `publishFiles` named the branch after `runId:patchHash`, so a new patch got a new branch and a new draft.

The same mechanism opens a second draft on one base whenever the base gets any commit and the regenerated patch differs by a byte. An unchanged patch hit `Refusing to overwrite` instead. Either way, every push to `main` could produce a duplicate or an error.

### What changed

- The branch is derived from the provider and target version (`draftKey()`), the base branch, the App and the integration. It no longer depends on the run, the revision or the patch bytes.
- `publishFiles` looks up the pull requests from that branch before writing.
  - A closed or merged one makes Refit return without writing anything.
  - An open one whose tip is still the commit Refit last pushed is moved onto the new base: a new commit, a ref moved under a lease on that commit, and a refreshed title and description, with the same number.
  - A branch with a person's commits, or a pull request someone else opened, is left as it is.
- `findExistingMigration` does the same check before generation, so declined, merged and customer-edited drafts cost no AI or validation.
- With `--supersede-drafts` only, once its draft is current, Refit closes its other open migration drafts for this provider and integration on the same base, each with a `Superseded by #N` comment. A draft with a person's commits stays open.
- The workflow reports `draft-updated` and `draft-closed` alongside `draft-created` and `existing-pr`. Slack still notifies only on `draft-created`.

Assumptions (recorded in the PR):

- Refit recognizes its own commit by the draft's record of the commit it last pushed. A draft from an earlier release, or a branch with no open draft, falls back to one parent plus the App bot as author and committer. A squash, merge or rebase a person makes on the branch fails both, so Refit stops updating it.
- A personal-token run cannot make that distinction. It reports an existing draft as it is and never overwrites a branch.
- Re-validating on every base push costs what the hosted worker already spends: its job key already includes the revision. The change is only that the result updates the draft instead of opening a new one.

### Evidence

- `pipeline/draft-lifecycle.test.ts` covers six scenarios against the simulated GitHub in `pipeline/fixtures/fake-github.ts`, with real Git objects, refs, pull requests and comments:
  - the full-stack-starter-kit sequence: a config-only commit on `main` and a different patch now give one draft, updated in place;
  - a rerun before generation;
  - customer commits;
  - closed and merged drafts;
  - superseding;
  - separate bases.
- Against the previous `publication.ts`, five of the six fail. The duplicate reproduces as a second pull request, or as `Refusing to overwrite`.
- `pipeline/publication.test.ts` covers token mode, races and the closed and merged short-circuits with a request-level mock.
- The Stripe benchmark never publishes (its flags may not contain `--publish`), and its scorer reads only statuses this slice leaves alone. So a benchmark run cannot show this change. Its measure is the simulated scenarios plus P1's rerun on Fly.

### Asked of P1 after merge

Deploy, then retry `refit-dev/full-stack-starter-kit`. Expected:

- The worker reuses PR #2 as the existing draft and opens no third one, because PR #2's marker still matches the unchanged `main`.
- PR #1 stays open. It is on `refit-base` from the benchmark publisher, which the hosted worker never sees. Closing it is a one-off manual step.
- The first push to `main` after the deploy opens one new draft beside PR #2: PR #2's marker hashes the old revision, its branch is not the new `draftKey()` branch, and it names no provider, so superseding (off on the hosted worker) would skip it anyway. Close PR #2 by hand once the new draft opens; later pushes update the new draft in place.

### P5's review and the owner decision (2026-10-24)

P5 sent this pull request back with five findings. The owner decided the first: Refit may force-update its own draft branch, but only with a lease. Superseding stays off by default.

1. **Force-update and superseding by default.** Refit records the commit it last pushed in the draft (`<!-- refit-pushed: <sha> -->`). It moves the branch with GitHub's GraphQL `updateRefs`, passing that commit as `beforeOid`, the equivalent of `git push --force-with-lease=<branch>:<sha>` (the `RefUpdate` and `UpdateRefsInput` reference, read 2026-10-24). If the branch holds anyone else's commit, Refit never forces: it leaves the branch and, when the base moved, keeps one comment on the draft saying so and which files its patch changes. That comment is edited, not repeated, when the base moves again. Before moving, the record names both the old and the new commit, so a run cut short between the two writes still recognizes its branch. Superseding needs `--supersede-drafts` on `refit run` or `refit serve`.
2. **The supersede match ignored the provider.** Drafts now carry `<!-- refit-provider: <id> -->`, and superseding requires it to match. A draft from an earlier release has no provider marker and is never closed.
3. **Refit's own closures read as a person's decline, and a reopened draft was closed again.** A closed draft whose `closed_by` is the App is not a decline, so a target that comes back gets a new draft. A draft that already has Refit's `Superseded by` comment is not closed again after a person reopens it.
4. **`draftKey` merged contracts that share one `info.version`.** When the target version equals the baseline's, the key uses the contract's breaking changes instead (not its snapshot, so an upstream edit that changes none of them keeps the draft).
5. **A force-update swapped the patch under reviews with no notice, and the race checks were untested.** After a move, a draft someone else reviewed gets a comment naming the old and new commits and why. The tests cover:
   - a person's push landing between Refit's description write and its ref move, through a one-shot hook in the fake GitHub. Without the lease, this test fails;
   - a pull request someone else opened from the Refit branch.

`pipeline/draft-lifecycle.test.ts` now has twelve scenarios. The fake GitHub gained GraphQL `updateRefs` (atomic, checks every `beforeOid` first), `closed_by`, comment listing (paginated) and editing, reviews, compare, and a pull request head that lags behind its branch.

A review of the lease change (one finder per area, each finding checked by a second agent) confirmed these, all fixed on this pull request:

- Ownership was judged from the pull request's reported head, which GitHub may update late. Refit now reads the branch.
- Two Refit runs on one draft could overwrite each other's record and hold the draft for good. Refit re-reads the draft before the move and adds the new commit to the record it finds. A run that stalls between that read and its write can still drop the other run's commit; that narrow case is commented as a shortcut.
- The reviewer notice counted any review. It now needs a review of the replaced commit, and it is posted, with the new description, right after the move rather than after later checks that can fail.
- A lease GitHub applied but reported as an error read as lost.
- Comment and review lists stopped at 100; they now page (up to 1,000).
- Superseding commented before closing, so a failed close left a marked open draft Refit then skipped. It now closes first, and skips a draft a person marked ready for review.
- `draftKey` by snapshot opened a new draft on any upstream edit; it now uses the breaking changes.
- `refit run --supersede-drafts` without `--github-app` did nothing; it is refused. `refit serve`'s refusal is tested.
- The held-draft comment before generation said the draft "migrates" files the scan found on the new base; it now says the scan finds usages there and asks to check the draft covers them.

Fixed in Laptop 1's review (2026-10-24): superseding compared no targets, so a retried job for an older target could close a newer draft. Drafts now record their target (`<!-- refit-target: <version> -->`), and superseding closes only a draft whose target sorts before this one's; a draft with no target record, or the same one, stays open. `pipeline/local-service.test.ts` now checks that `refit serve` passes `--supersede-drafts` through to publication. Still open: a retried job for an older target whose draft Refit closed as superseded opens that draft again beside the newer one; it no longer closes the newer one.

## Slice 2: after the merge

### What happened before

Read from the code at `fc4dc00` plus slice 1:

| After Refit's draft       | Watcher (`refit watch`, operator-configured `refit serve`)                                                                  | Approved target (`refit serve`, hosted worker)                                                                                                                                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Merged                    | Next poll: `needs-review` (the code's pin conflicts with the configured one). Each new commit on the base adds another stop | Every poll stops in `loadApprovedRepository` → `inspectEnrollmentInputs` (`repository-enrollment.ts:210`): "Declared SDK API version … conflicts with the application pin". The next release is never compared, and only a new approval with a new committed baseline recovers it |
| Closed unmerged           | Never reopened or replaced (slice 1)                                                                                        | Same                                                                                                                                                                                                                                                                              |
| Customer migrates by hand | The open draft stays open forever; the run stops for review                                                                 | Same, after the enrollment stop                                                                                                                                                                                                                                                   |

`AUTOMATION.md` said so: "Refit does not advance the baseline after a PR".

### What changed

- **`up-to-date`, a quiet status (exit 0).** `runWorkflow` returns it before any AI, validation or publication when the target is reached (`targetReached()` in `migration-review.ts`). Reached means:
  - every SDK client Refit can read sends the target (`declaresVersion()`; a missing or dynamic pin never counts);
  - Refit finds no use of what the target breaks: no finding of either confidence (untraced reads count, per the 2026-10-21 owner decision) and no traced breaking call;
  - no file was skipped.
- **Self-fix closes the draft once.** If the target is reached and Refit's own open draft for it exists, Refit closes it, then comments with the reason and a `<!-- refit-resolved -->` marker. A draft a person marked ready for review stays open. If the reads are migrated but the pin did not move (`NO_USAGE_REASON` with no findings at all), Refit closes the draft as `draft-closed`. A person who reopens the draft keeps it open: the marker is never written twice. Only App mode, a clean checkout and a base that matches GitHub close anything; the base is checked once a draft to close is found, so a run with no draft never fails on a moved base.
- **The watcher advances its baseline.** When the workflow says `up-to-date` and the watcher's own scan agrees that the target is reached, `watch.ts` copies the target to `snapshots/<hash>.baseline.json` and records `state.baseline = { hash, apiVersion, revision }`. Later polls use it as `before` and its version as `apiVersion`. The hash is checked on every read. `watchCarryOver` already carries `*.baseline.json`, so hosted job machines keep it. Until the next release, later commits return `already-processed` with `up-to-date` and run nothing.
- **Approved targets get past enrollment.** `service-worker.ts` passes `watchedApiVersions(stateDirectory)` (the last captured target and the advanced baseline) to `loadApprovedRepository`. Enrollment then accepts a client pin that verifies against one of them. Everything else (the fingerprint, other pins, unreadable clients) stops as before.

Edits outside P4's files, all additive:

- `api-version.ts` (F2): export `specificationVersion`; add `declaresVersion`.
- `repository-enrollment.ts` (P3): the `acceptedApiVersions` option, 6 lines. P3's `feat/p3-zero-config` touches neighbouring lines, so the merge conflict is mechanical.
- `service-worker.ts` (unowned): one argument.
- `stripe-benchmark.ts` (O5): `workflowScanStop` leaves a reached target to `refit run`, as the workflow does.
- `workflow.ts` (shared): the `up-to-date` exit and the resolved-draft closes.

### Evidence

- `pipeline/draft-lifecycle.test.ts`, six new scenarios against simulated GitHub, through the real `runWorkflow` on a Git checkout:
  - a customer migrates and moves the pin: the draft is closed once with the note, a reopened draft stays open, and there are no new comments;
  - the reads are migrated but the pin is unchanged: `draft-closed`;
  - nothing to do and no draft: no pull request and no comment, also when `main` moves on GitHub during the scan;
  - a draft a person marked ready for review stays open;
  - an untraced read of a removed field remains: the draft stays open and the run stops for review. On the confirmed-only rule this test fails with `up-to-date`.
- `pipeline/watch.test.ts`: a merged repository advances the baseline. A job machine started from `watchCarryOver` files alone compares the next release with that target (with `before`, `apiVersion` and the `source-verified` policy asserted), and a tampered baseline file stops.
- `pipeline/migration-review.test.ts`: a merged repository reaches its target with a removed field it no longer reads, and not with a breaking change outside the rules.
- `pipeline/repository-enrollment.test.ts`: an approved repository whose client moved to the watcher's target loads. A different version, or an unreadable client, still stops.
- Identical before and after contracts keep their `refit run` result (`needs-review`, exit 2). An earlier version of this slice made them `up-to-date`, which broke 12 tests in five other suites, among them O5's benchmark mirror ("decides an unchanged contract exactly as the workflow does"). The quiet case lives in the watcher instead.
- `pipeline/stripe-benchmark-workflow.test.ts`: the harness leaves a reached target to `refit run`, which reports `up-to-date`, so the harness still decides exactly as the workflow does.
- No benchmark before and after. Every frozen Stripe list excludes repositories already on their target: the original 100 and the held-out 50 need "an upgrade ahead", and the fresh 381 dropped the "2 … already on the target". So the new exit cannot fire on any row, and the statuses the scorer reads are unchanged.

### Assumptions

- `up-to-date` is safe to report without validation, because nothing is proposed or published. The close note says what Refit saw, and reopening is the override.
- The advance needs the evidence a draft needs, so it cannot hide a breaking usage: every breaking change outside the rules still stops it, except a removed response field the scanner searched for and found no read of (Laptop 1's review, 2026-10-24; before, `targetReached` ignored unmapped changes, so a hand migration with, say, a newly required request parameter reported `up-to-date`). A file Refit skipped, or a client it cannot read, blocks it. After the advance the watcher compares under `source-verified`, since nobody attested the target as a pin.
- Closing on "no usages" trusts the scanner. A Refit release that lost track of a client would close a valid draft. The note says what Refit saw, a person can reopen it, and Refit then leaves it open.
- A new release that lands before the watcher sees the merged code compares the old baseline with the new release, and stops for review on the pin. A retry does not recover it: the watcher then accepts only the newer release's version. Moving the committed baseline and `.refit.json` pin to the merged version (with a new approval for an approved target) does.

### Not covered

Zero-config repositories (P3's `feat/p3-zero-config`) derive `before` from the version the code sends. After a merge, the generated configuration and contract change, and so does the approval fingerprint. Asked P3 on the board whether the approval should follow the generated version or need a new approval.

By default #1 stays open; with `--supersede-drafts` it is closed with `Superseded by #2` (the test runs both). After merging #2, the baseline advances straight to endive.

### Bug found and fixed

The watcher's job key covered the changes Refit maps but not the target version. A newer release whose mapped changes matched (endive adds only a request-parameter removal, which is a finding, not a mapped change) counted as already processed, so no draft for it ever opened.

The key now includes `apiVersion.after`. A documentation-only revision keeps its version, so it still deduplicates. The old watch test's "documentation-only" edit deleted `info.version`; it now keeps it.

**Effect on deploy (for P1):** every existing job key changes, so each hosted target runs once more after deploy:

- A target with a current Refit draft finds it before generation (no AI, no validation).
- A target that stops for review records the same stop again.
- A target that validated without publishing validates once more.
- A target whose last job reached generation or validation and did not publish (checks failed, or passed with findings left) runs them again. The live worker runs with `--ai-patch --repair-attempts 2`, so such a target spends AI once more, within the configured budget caps.
- Local `refit watch` and `refit serve` state reruns each target once the same way.

### Evidence

- Both replay scenarios pass with the default `npm test` (no Docker, database or network).
- On slice 1's code, the replay fails at the first poll after the merge: `RepositoryApprovalError: Repository configuration needs review: Declared SDK API version 2025-04-30.basil at billing.js:4 conflicts with the application pin 2025-02-24.acacia.`
- Without the job-key fix, the cumulative scenario fails: the endive poll reports `draft-created: Saved worker result reused` and no draft #2 appears.
- `pipeline/watch.test.ts`: a new version with the same changes is a new job.

### Not covered

Someone merges Refit's older draft after a newer release stopped for review. Enrollment then stops on the pin until someone approves a configuration whose baseline is the merged version. Resolving it automatically needs the watcher to keep each drafted target's contract and pick the baseline from the version the code sends. That overlaps P3's version-derived baselines.

## Design questions

**What happens when the customer pushes commits to the draft branch?**

Refit stops writing to that draft and tells the person so, before spending AI or validation. When the base has moved under the branch, it also says so once on the draft. Force-moving a branch with someone else's commits would destroy their work, and rebasing them needs conflict handling Refit cannot validate. Since the owner's decision, the lease enforces this at the moment of the write too.

The test shows it: a pushed commit leaves the branch tip, the description and the pull request untouched while `main` moves, and the run reports `The draft branch has commits Refit did not write, so Refit left it as it is.`

**Should one draft carry several version jumps, or one per release?**

One new draft per release, targeting the newest release, cumulative from the version the code sends now. When the customer merges each draft before the next release, that is one draft per release. When they do not, the older draft stays open beside the newer one unless `--supersede-drafts` is on.

This is how slices 1 and 2 behave:

- The draft key is the target version.
- With `--supersede-drafts`, a newer target's draft supersedes the older one with a link. Without it (the default since the owner's decision of 2026-10-24), the older draft stays open.
- The baseline moves only once the code reaches a target.
- So if release N's draft is still open when N+1 lands, the watcher compares the code's current baseline with N+1 and opens one draft for both jumps. N's draft is closed as superseded only with the flag. If a person merges N's draft instead, the code sends a version that is neither the baseline nor the watcher's target, and the approved target stops on the pin until a new approval.

Two stacked drafts would edit the same lines and the same pin. Merging the first would leave the second in conflict and validated against code that no longer exists. A cumulative draft is validated against the code as it is, at the version it will run.

The cost is a bigger diff when a customer skips releases. The body still lists each change with its evidence. Tested in slice 3: `pipeline/release-replay.test.ts` covers both the one-draft-per-release path and the cumulative draft.

# L3: Stripe breaking-change catalog (basil to endive)

Every change the docs.stripe.com changelog marks **Breaking** for the four major releases, with what Refit does with it today. Entries: `docs/benchmarks/stripe-changelog/catalog/<version>/<slug>.json`; tests: `pipeline/stripe-changelog-catalog.test.ts`.

## Sources and scope

- The changelog index (https://docs.stripe.com/changelog.md) and every linked change page (`<page>.md`) were fetched with curl on 2026-10-24 between 23:14 and 23:16 UTC; all 79 returned 200, so nothing is **Blocked**. Every entry has `checkedAt: 2026-10-24` and cites its page.
- Versions, from the index: `2025-03-31.basil`, `2025-09-30.clover`, `2026-03-25.dahlia`, `2026-09-30.endive`. Their monthly GA releases (2025-04-30 to 2025-08-27.basil, 2025-10-29 to 2026-02-25.clover, 2026-04-22 to 2026-08-26.dahlia) mark **no** change Breaking. `.preview` releases (public preview channel) do mark some, and are out of scope: they are not GA versions a pin moves to.
- Contract facts (which fields the recorded contracts declare, which enums gained values) come from the stripe/openapi `spec3.json` tags recorded in `data/stripe-openapi-versions.json`, checked by SHA-256. stripe-node method names come from the docs.stripe.com API reference (`?lang=node`), read the same day.

## Handling values

- `rule`: an existing deterministic rule edits the code (module and function named).
- `generic`: Refit's existing contract comparison reports it and its existing behaviour is the whole handling. Every `generic` part here is a response enum addition that only fullDiff reports (where traced code switches over the field or compares it with string literals, owner decision 6).
- `ai`: reported as a confirmed finding with no rule; a deterministic patch leaves it unresolved and the AI patch path receives it.
- `stop`: Refit stops for review with a named reason.
- `none` (added to the brief's four values): Refit has no signal at all: a behaviour change outside the contracts, a Stripe.js change, an API v2 change (spec3.json has no `/v2` paths), or an SDK call the adapter does not map. Calling these `ai` or `stop` would claim a reaction that does not happen.
- `(fullDiff)`: only the oasdiff comparison sees it. That is the hosted worker and the benchmark's production mode; `refit run` and the benchmark fix stage run with fullDiff off and report nothing for these. Under fullDiff a request change stops **every** traced call of the operation, whether or not the call sends the changed value.
- The engine path is the benchmark's: the generated SDK-spec adapter (`stripeOperations`, `repositoryAdapter`), then `run.ts`'s order. An entry counts as handled only when every part is `generic` or `rule`.

## Findings while classifying

1. **Unmapped SDK calls.** Both adapters name stripe-node resources from the URL. So `invoiceItems.*` (`/v1/invoiceitems`), `invoices.createPreview` (`/v1/invoices/create_preview`), `subscriptionItems.createUsageRecord` and `invoices.listUpcomingLines` are never mapped, and their removed request parameters (`price`, `unit_amount`, `coupon`, `iterations`, `billing_cycle_anchor`) are reported nowhere. Fixtures pin this.
2. **Built-in adapter gap.** The built-in adapter (`STRIPE` plus `stripeAdapterFor`, which `refit run` and the hosted worker use without a provider config) keeps its own `paymentIntents.*` operations, and those have no `operationId`. So `removedRequestParameters` skips them, and `paymentIntents.create/update/confirm({ payment_method_types })` is not reported at all, `['card']` included. Only the benchmark's SDK-spec adapter sees them. Seen with a probe on the real 2026-08-26.dahlia and 2026-09-30.endive contracts; not pinned by a test.
3. **Reads behind `anyOf`.** The analyzer follows nested schemas only through direct `$ref`s. Fields behind a nullable `anyOf` (`subscription.cancellation_details`, `charge.payment_method_details`, `price.recurring`, `customer.discount`) are never traced. So the dahlia retention-policy reason and the endive `data_share_only` value go unreported even under fullDiff, and `price.recurring.aggregate_usage` is only a review finding.
4. **Equality checks.** Since owner decision 6 (5bb8562f), `switchedEnumAdditions` also sees literal compares (`===`, `!==`, `==`, `!=`, `['a'].includes(...)`), so under fullDiff code comparing a replaced value (`ui_mode === 'hosted'`, `status === 'reversed'`) stops for review, but only because the same release adds values to that field, and the entry names the added values. A value that is renamed or removed with no addition on a traced field, or a read that neither compares nor switches, is still unreported.

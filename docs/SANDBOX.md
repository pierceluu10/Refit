# Docker sandbox

Refit runs a repository's own commands only inside Docker, as checks before and after a patch. Dependency installation also runs in Docker, but executes only Refit's pinned package manager and no repository code. Every `docker run` Refit issues is built by `dockerSandboxArguments` in `pipeline/docker-sandbox.ts`. There are two callers: `containerCheck` in `pipeline/validation.ts` (configured and generated checks) and `installDependencies` in `pipeline/dependency-preparation.ts` (dependency preparation). The only other Docker commands are `image inspect`, `ps`, `rm` and, for generated checks, `create` and `cp` to copy the stripe-mock binary out of an operator-installed image. None of these runs repository code.

This page lists each control, the test that enforces it, and the risks Refit accepts. The hosted worker's wider threat model (webhooks, approvals, secrets) is in `docs/SECURITY.md`.

## Controls

Unit tests run in the default suite. Gated tests run with `REFIT_DOCKER_IMAGE=node:22-alpine`, and the postinstall case also needs `REFIT_NPM_PREPARE=1`:

```sh
REFIT_DOCKER_IMAGE=node:22-alpine REFIT_NPM_PREPARE=1 npx vitest run pipeline/docker-sandbox-docker.test.ts --maxWorkers=1
```

`pipeline/docker-sandbox.test.ts` asserts the exact argument list for a validation check, a check with dependencies and mounts, and a preparation run, so adding, removing or reordering a flag fails a test. ## Accepted risks

- **Shared kernel.** Containers share the Docker host's kernel. A kernel or runtime exploit escapes every control above. On the hosted worker, per-job machines (PG3) are the next layer.
- **Docker access.** Refit runs the `docker` CLI, which is root-equivalent on the Docker host. Refit never gives a container the Docker socket.
- **Preparation network.** The installer container uses `bridge` networking, so it can reach anything the Docker host's network reaches: private addresses and cloud metadata endpoints as well as the npm registry. Only Refit's pinned package manager runs there, on manifest-only inputs and with lifecycle scripts disabled. On EC2, an IMDSv2 hop limit of 1 keeps containers away from instance credentials.
- **Python preparation network.** Python preparation (`pipeline/python/validation.ts`, see [Python validation](PYTHON-VALIDATION.md)) also uses `bridge` networking, through the same `dockerSandboxArguments`. It runs pip (and, for uv and Poetry lockfiles, those tools at pinned versions) on the repository's dependency files with wheels only, so no package build code runs unless `REFIT_PYTHON_SOURCE_BUILDS=1`. pip reads the repository's requirements files, which may name another index.
- **Seccomp default.** Refit relies on the daemon's default seccomp profile. A daemon configured to run unconfined by default would remove it; the gated test reports `Seccomp: 2` on the host where it runs.
- **Orphan window.** A container left by a killed Refit process keeps running, inside its CPU, memory and process limits, until the next Refit sandbox run on that Docker host removes it.
- **Shared memory.** `/dev/shm` keeps Docker's 64 MiB default; it counts against the container's memory limit.
- **Archive extraction inside the container.** A hostile dependency archive is unpacked in the same container that runs the repository's untrusted checks, so it can do nothing the checks could not do already.

## Overhead

Measured on 2026-10-22 with Refit at `0dda480`, on a MacBook running Docker Desktop (8 GB VM) that six other Refit sessions were also using. For each repository, dependencies were prepared once with `prepareDependencies`. Then the benchmark's own typecheck (`npx --no-install tsc --noEmit --pretty false -p .`) ran in the validation sandbox 3 times per variant, in round-robin order: `main`'s flags, `main` plus each new flag alone, and every flag (this branch). The five repositories are the first five npm projects whose typecheck validated in `2026-10-16-stripe-fixrate-original-results.json`, at their frozen commits. The `--memory-swap` column was measured on the branch; the flag was removed before merge pending an owner decision. These timings are not backed by a committed results file.

airbnb-clone exits 2 on type errors it already has at that commit (its Prisma client is not generated), as it did in the benchmark, where `compareTypeErrors` counts only errors a patch introduces.

No flag shows a consistent overhead. The all-flags median is between 0.70 and 1.16 times `main`'s. Two single-flag medians stand out, both on google-drive-clone: `--log-driver none` at 1.86 times `main` and `--ulimit core=0` at 1.60 times. On the same repository, the variant with every flag, which includes both, had a median of 8.3 s (1.10 times), `--log-driver none` is within 0.92 to 1.01 times on the other four repositories, and `--ulimit core=0` within 0.95 to 1.22 times; its 1.22 (thumbnail-critique, 14.9 s) is inside `main`'s own range there (10.7–17.4 s). We read both as noise from the shared host, not as a cost of the flag. A quieter host and more runs would be needed to resolve differences below about 20%. The reaper adds about 19 ms to each sandbox start, which is under 1% of every check measured here.

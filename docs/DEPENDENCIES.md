# Automatic validation dependencies

Refit can prepare dependencies from a clean repository's committed `package.json` and `package-lock.json`, then run its checks in an ordinary local Node Docker image. This removes the custom dependency-image setup for supported npm projects. The same preparation works through `run`, `validate`, `watch` and service profiles.

Pinned pnpm projects and bounded workspaces use the same commands with `pnpm-lock.yaml`. Catalogs, explicit workspace links and pnpm's separate manager/application lock documents are supported. See [pnpm setup and limits](PNPM-WORKSPACES.md).

Positive-glob npm workspaces with committed manifests and root lockfiles are supported through the same preparation. Workspace links and nested dependency directories are verified and retained. See [workspace setup and boundaries](NPM-WORKSPACES.md).

## Test the Stripe pipeline

The local Docker daemon must be running and `node:22-alpine` must already be installed. Refit never pulls a base image automatically. If needed, download it explicitly with `docker pull node:22-alpine`.

From the Refit checkout, run the installed App with the prepared npm profile:

```sh
cd ~/Repos/Refit
refit serve --env .env --config examples/local-service.npm.refit.json \
  --state ~/.refit/stripe-prepared-pilot --once
```

This discovers the installed App's access, fetches the billing demo into a managed checkout, scans the supplied historical Stripe contracts, prepares dependencies when necessary, and validates a deterministic migration. The example checks original behavior, both original/changed behavior after patching, and TypeScript. It leaves your billing checkout unchanged and does not publish a PR. Subsequent polls reuse the saved job and report that checks were not rerun. Omit `--once` for continuous polling.

For draft publication, use a **fresh service state directory** and add `--publish-draft`. PR #3 predates the approved configuration merge and does not cover the current monitored base. Refit reuses an App draft only when its base and migration identity match; publication can create a new draft after validation. See [the current App evaluation](AUTOMATION.md). To evaluate a new AI proposal locally, add `--ai-patch --repair-attempts 1` with fresh state and your shared spending allowance:

```sh
REFIT_AI_BUDGET_USD=2 \
REFIT_AI_BUDGET_DIRECTORY=~/.refit/evaluations/2026-10-12 \
refit serve --env .env --config examples/local-service.npm.refit.json \
  --state ~/.refit/stripe-prepared-ai-pilot \
  --once --ai-patch --repair-attempts 1
```

This uses the existing project allowance rather than resetting spending. AI generation and publication remain explicit. Configuring a different source or baseline uses the same environment preparation; the historical sample does not discover a new live Stripe change.

## Prepare or validate a local repository

Inspect dependency preparation independently:

```sh
refit prepare --repository ~/Repos/refit-billing-demo \
  --image node:22-alpine
```

It prints the recorded Node/npm versions, number of locked package records and evidence path. This is not a count of installed packages: platform-specific optional records can be skipped by npm. `--json` supplies machine output. `--cache /absolute/path/outside-git` chooses a cache explicitly; otherwise `REFIT_DEPENDENCY_CACHE_DIRECTORY` or `~/.refit/dependencies` is used. An empty environment setting uses the default. The cache is capped at `REFIT_DEPENDENCY_CACHE_GIB` (a whole number of GiB from 1 to 1024, default 8); see [cache, evidence and recovery](#cache-evidence-and-recovery).

You can also opt in on a run without creating a service:

```sh
refit run --repository ~/Repos/refit-billing-demo \
  --before pipeline/fixtures/before.json --after pipeline/fixtures/after.json \
  --output /tmp/new-refit-prepared-run --image node:22-alpine \
  --prepare-dependencies --baseline-command '["npm","test"]' \
  --command '["sh","-c","npm test && npm run test:after && npm run typecheck"]' \
  --human
```

Or add `"prepareDependencies": true` to a workflow file. `image` then names the existing Node base image; your commands can use ordinary `npm test` and `npm run ...` without linking a custom image's dependency directory. The prepared service example uses [this workflow](../examples/billing-demo.npm.refit.json).

## Installation and checks

Preparation reads committed root manifest/lock files and selected workspace manifests. It verifies public registry package URLs and integrity records before starting a container. `npm ci` installs frozen dependencies, including development dependencies, with install lifecycle scripts, audit and funding requests disabled. If it rejects the lockfile's peer dependencies (`ERESOLVE`), or reports the lockfile out of sync (`EUSAGE`, as for a lockfile written with `--legacy-peer-deps`), Refit retries once with `--legacy-peer-deps` on the same lockfile and records `installation.legacyPeerDeps` in `environment.json` and the draft. The retry validates the lockfile again without peer edges, so a lockfile that is out of sync for any other reason still stops, and what installs is exactly the locked tree. On a musl image such as `node:22-alpine`, a lockfile that records no `libc` makes `npm ci` install the glibc builds of native packages too (`@next/swc`, `@swc/core`, `sharp`), which cannot load there. After the verified, script-free install, Refit removes each installed package whose own `package.json` excludes musl and that declares no `bin`, records the count as `installation.prunedGlibcPackages` in `environment.json` and states it in the draft. The lockfile is unchanged; pnpm and Yarn 2+ already skip such packages. pnpm uses its declared pinned manager and frozen lockfile instead. Engine requirements are enforced. Separate empty npm configuration files override image-level configuration; repository `.npmrc`, `.env`, source files and host credentials are not provided to the installer. The one exception is read on the host: a root `.npmrc` line `legacy-peer-deps=true` adds `--legacy-peer-deps` to `npm ci`, for lockfiles generated with it, and is part of the dependency cache key. Every other `.npmrc` setting, including the registry, is still ignored. No repository Dockerfile or build script runs during preparation.

The installer has bridge networking to download public npm packages, runs as a non-root user, and uses the same restricted Docker resources as validation: read-only root filesystem, no capabilities, no privilege escalation, 1 CPU, 1 GiB memory, 128 processes and a bounded writable workspace. By default (owner decision, 2026-10-24) the installer and validation containers both get a 4 GiB workspace and 5 GiB of memory, with a 2 GiB dependency archive limit: the package cache and the unpacked tree coexist during installation, tmpfs counts against container memory, and the archive is unpacked into the validation workspace. Each container may claim 5 GiB, so the Docker host needs 8 GiB and runs one such check at a time. `REFIT_VALIDATION_WORKSPACE` selects a smaller profile on a smaller host: `2g` (3 GiB memory, 1 GiB archive), `1g` (2 GiB memory, 512 MiB archive) or `512m` (1 GiB memory, 256 MiB archive); under these the installer keeps a 2 GiB workspace and 3 GiB of memory. It changes no other restriction. `REFIT_VALIDATION_OVERLAP=1` lets one validation run its patched side and the baseline in two sandboxes at once, only when `docker info` reports room for both; it is off by default, and an operator running several validations on one host should leave it off. Network stays disabled in every profile, and the report and dependency evidence record the workspace and memory used. Before archiving, Refit checks dependency symlinks resolve inside `node_modules`; broken or escaping links and special files fail preparation. Preparation has a 300-second deadline, the validation profile's archive limit (2 GiB by default, 1 GiB under `2g`) and a 1 MiB log limit. For a larger dependency tree, set `REFIT_DEPENDENCY_TIMEOUT_SECONDS` to a whole number from 60 to 1800; the evidence records the deadline used. CPU, process and validation limits do not change. Cancelled, failed or excessive output stops the client and removes the container; no successful cache is published.

Validation snapshots the verified dependency archive into its own private temporary directory. Both baseline and patched containers extract that same snapshot into their temporary workspace, with **network disabled**. The configured application checks execute there. A passing installation is not a passing test or migration; baseline failures still stop before AI generation.

The committed source is copied into the same validation workspace, so it has its own limit: 512 MiB under the `4g` profile, 256 MiB under `2g` and 50 MiB under smaller ones (founders' decision, 2026-10-27; the largest committed tree on the frozen Stripe lists is 155.5 MiB, see [Dependency blockers](DEPENDENCY-BLOCKERS.md)). A larger committed tree stops validation with a message that names what to stop committing (build output, media or data files, or files that belong in Git LFS).

## Generated clients

Preparation runs no install scripts and checks run on a clean checkout, so a Prisma client that `postinstall` or a developer generates, and the `next-env.d.ts` that `next dev` writes, are missing in validation: 58 of 189 l2-push-249 type checks report `@prisma/client` with no exported members, and models typed `any` hide real type errors. Each check's offline sandbox first runs `prisma generate` with the locked Prisma CLI and placeholder engine paths, when the root `package.json` declares exactly that `postinstall` or declares `@prisma/client` and commits a schema where `prisma generate` finds it, and writes the `next-env.d.ts` references Next writes when `tsconfig.json` includes the file and it is not committed ([`declared-generators.ts`](../pipeline/declared-generators.ts)). Each generator's command, environment and exit code are recorded on the check (`generators`), the check runs whatever they return, and neither file reaches the patch. It is on by default since the founder's decision of 2026-10-28, which superseded the removal of 2026-10-22: generation runs offline from the committed schema and the packages prepared from the committed lockfile, with no downloads, no lifecycle scripts beyond the generator and no secrets. `REFIT_GENERATE_CLIENTS=0` (`--skip-generated-clients` on the Stripe benchmark) turns it off. On l2-push-249 it clears the missing-client type errors in 71 of 73 rows with no outcome change, and patches are unchanged. See [Preparation failures](PREPARATION-FAILURES.md#generated-clients-behind-a-flag) and [Benchmarks](BENCHMARKS.md#runtime-stand-ins-and-generated-clients-october-28).

## Cache, evidence and recovery

Cache identity includes the exact committed manifest and lock bytes, immutable Docker image ID and preparation recipe version. Completed bundles are atomically published and include `dependencies.tar`, `environment.json`, `install.log` and an unsigned hash manifest. Refit verifies file types, hashes, sizes and input identity before reuse. Truncated, changed or incomplete existing bundles stop rather than silently reinstalling. Changing manifests or images creates a different cache entry.

Each new bundle is followed by eviction: Refit removes the least recently used bundles until the cache fits `REFIT_DEPENDENCY_CACHE_GIB` (default 8 GiB; a value that is not a whole number from 1 to 1024 stops preparation before it installs anything). A reuse counts as use. Eviction takes each bundle's preparation lock, so a bundle another process is preparing, verifying or copying for validation is skipped, and validation copies the archive while it holds that lock. It unpublishes a bundle with one rename before deleting it, so an interrupted eviction never leaves a partial bundle; the next preparation of that input installs it again. The bundle just written is never evicted, even when it alone exceeds the cap. A preparation that starts during the instant an eviction holds its lock fails on the lock, like two concurrent preparations of the same input.

Use `refit verify --directory /absolute/path/to/bundle` for byte integrity. Verification does not authenticate the producer, audit npm packages or establish application behavior. Review `install.log` and input identity before removing an invalid bundle and deliberately preparing it again. Cache and worker state must remain outside Git repositories, including through directory symlinks. Active preparation locks are refused; a verified dead owner can be recovered using the existing state-lock rules.

Validation reports and collapsed PR evidence record the runtime, image, input hashes, dependency archive hash, preparation policy and whether the cache was reused. Human output summarizes dependency preparation separately from check results. Previous configurations without preparation retain their worker identity; enabling preparation needs fresh worker/service state.

## Supported projects

Automatic npm preparation supports a root project or bounded positive-glob workspaces with a committed lockfile version 2 or 3, dependency declarations the lockfile satisfies, and public `registry.npmjs.org` HTTPS tarballs with SHA-256-or-stronger integrity. An integrity that lists a `sha1` hash beside a SHA-256-or-stronger one is accepted, because npm, pnpm and Yarn 1 check only the strongest algorithm listed (ssri's `pickAlgorithm`). A leftover `extraneous` record outside every `node_modules` directory with no `link`, `resolved` or `integrity` is skipped: it describes a project directory, which npm never fetches. As `npm ci` does (npm 10.9's `lib/utils/validate-lockfile.js` and Arborist's `dep-valid.js`), a declaration that differs from the lockfile's root or workspace record is accepted when the version the lockfile installs for it (the nearest `node_modules` entry) satisfies the declared range, and a record `package.json` no longer declares is pruned, so the committed lockfile installs unchanged. A declaration it does not satisfy or does not lock refuses, naming it; prereleases, tags and aliases are never compared, so drift on them refuses too. A record npm marks `inBundle` ships inside its nearest non-bundled ancestor's tarball, so it is accepted without its own source only when it records a version, carries no `resolved` or `integrity` of its own, and that ancestor passes the same registry and integrity checks (the `npm` package's bundled dependencies are the common case). [pnpm](PNPM-WORKSPACES.md) has its own pinned-manager and lockfile-v9 requirements. Preparation inputs are limited to 512 KiB per manifest/configuration, 8 MiB for the lockfile and 20,000 package records per graph; the scanner's existing repository limits also apply. The image must already contain compatible Node, npm, `/bin/sh` and `tar`.

A root project that commits only Bun's text lockfile (`bun.lock`, lockfile version 1) is installed through npm. Refit translates `bun.lock` into the npm lockfile of the same tree: each package at the `node_modules` path its key names, from its `registry.npmjs.org` tarball with Bun's sha512 integrity, bundled packages as `inBundle`, and every package no chain of required dependencies reaches marked optional, so npm skips other platforms' binaries as Bun does. `npm ci` then installs that lockfile like a committed one, with scripts off and every tarball checked against its integrity; Bun itself never runs, and the draft says so. Bun reads `bun.lock` before `bun.lockb`, so a binary lockfile committed beside it is ignored. Preparation stops when a package is not a public registry package with integrity, when `bun.lock` disagrees with `package.json`, for workspaces, for a committed `bunfig.toml` (it can change the registry or the layout), and when npm cannot describe Bun's tree: a peer Bun nests inside the package that needs it (npm resolves a peer from that package's parent), a dependency the tree leaves unresolved, or a package nothing reaches. Package `engines` are not in `bun.lock`, so `--engine-strict` has nothing to check for these trees.

A repository that commits more than one of `package-lock.json`, `pnpm-lock.yaml` and `yarn.lock` at its root has one of them installed, picked by the first rule that applies (founder decision, Otabek, 2026-10-28; `chosenLockfile` in `pipeline/dependency-inputs.ts`):

1. `package.json` pins npm, pnpm or Yarn with `packageManager`, that manager's lockfile is committed, and no committed GitHub workflow installs dependencies with another manager.
2. Without a pin, the committed GitHub workflows install dependencies with exactly one manager, and its lockfile is committed.
3. Without a pin or a workflow install: of the lockfiles Refit does not refuse as out of sync with `package.json`, the only one, or else the one whose last commit is strictly newer than every other's. The dates come from the checkout's own Git history; a shallow checkout or a tie picks none. The managed GitHub checkout and the Stripe benchmark clone fetch that history without file contents (`--filter=blob:none`) when a commit has several root lockfiles.

The chosen lockfile then has to pass every check on its own, and nothing falls back to another: a chosen lockfile refused for missing integrity, or whose `npm ci` fails, stops with that reason. Where no rule picks one (a pin for a manager whose lockfile is not committed, a pin another manager's workflow contradicts, workflows that install with two managers, lockfiles committed together, none in sync), the repository keeps its `conflicting-dependency-files` stop. Tracked `node_modules`, `npm-shrinkwrap.json` and pnpm hooks keep stopping. The other lockfiles are never read for installation; the draft names the one installed, the rule and what each other one shows, and check selection runs the tests with the chosen lockfile's manager. Validation makes the choice once, on the original commit, and the patched candidate reuses it, because a candidate's one-commit history cannot date its lockfiles.

Yarn 1 root projects and bounded Yarn 1 workspaces use the same preparation with a committed `yarn.lock`. Every lock entry must resolve an exact version to a public `registry.yarnpkg.com` or `registry.npmjs.org` tarball with SHA-256-or-stronger integrity, and every root dependency range must be recorded in the lockfile. Refit installs the pinned Yarn 1 release from `packageManager` (default 1.22.22) through npm, verifies its version and registry integrity, and runs `yarn install --frozen-lockfile --ignore-scripts --no-default-rc` with a private HOME. Only `package.json` and `yarn.lock` enter the installer; repository `.yarnrc`/`.npmrc` files do not. `yarn` is on PATH for offline checks. Workspaces use up to 64 positive patterns, as a list or `{ packages }`. Names must be unique, and sibling dependencies must use `*` or the sibling's exact version; Refit verifies each root `node_modules/<name>` link. `nohoist`, workspace CLI bins, git or local sources, and `yarn.lock` committed alongside another lockfile (unless one is chosen as above) fall back to the repository's own install (below).

Yarn 2+ root projects are prepared when `package.json` pins an exact `yarn@2`–`yarn@4` version and `.yarnrc.yml` sets only `nodeLinker: node-modules` (plus optional `enableTelemetry`). Every lock entry must resolve an exact npm version with a checksum. Yarn's built-in `compat` patches are accepted because they ship inside the pinned Yarn bundle, but repository patches are not. Refit installs `@yarnpkg/cli-dist` through npm, verifies a Corepack `+sha512` pin against the bundled `yarn.js`, and configures the install only through environment variables: node-modules linker, scripts off, private cache, immutable lockfile. Repository `.yarnrc.yml` and `.npmrc` never reach the installer. Yarn rewrites manifests it would format differently, so `package.json` must already match Yarn's formatting (sorted dependencies); otherwise preparation stops instead of changing a committed input. Plug'n'Play, Yarn 2+ workspaces, and lockfiles with platform packages that lack checksums (common for `@esbuild/*`) fall back to the repository's own install (below), because Refit's own preparation would install those packages unverified.

Scans and readiness also read a root `yarn.lock`, both Yarn 1 (`# yarn lockfile v1`) and Yarn 2+ (`__metadata`), to record the SDK version for the exact manifest range. A version is recorded only for a public registry resolution. Aliased, workspace, patched, git and local sources stay unknown. So does a repository that commits `yarn.lock` alongside another package-manager lockfile, or a `yarn.lock` the reader cannot parse.

## Nested packages

When every file the scan reports, each finding and each API-version declaration, belongs to one nested package that declares `stripe` and commits its own lockfile, Refit prepares and checks that package instead of the repository root (`pipeline/preparation-packages.ts`). A file belongs to the nearest `package.json` above it that declares `stripe`, the package Node resolves the SDK from. Preparation reads that package's `package.json`, lockfile and workspaces from the same commit and installs them exactly as it installs a root project: frozen lockfile, public registry tarballs with verified integrity, lifecycle scripts off, then offline checks. A tracked `node_modules` anywhere in the repository is still refused, because Node resolves modules up the directory tree. The validation sandbox copies the whole committed repository, unpacks the package's dependencies into the package directory and runs `command` and `baselineCommand` there, so checks can still read files outside the package. The Stripe benchmark selects that package's own check (`selectCheck`): its `test` script, lockfile, TypeScript and `tsconfig.json`, with every path in the command relative to the package, and validation grades it from there. Reports record `validation.packageDirectory`.

Everything else keeps the repository root, as before: files in the root package, files spread over several packages, and a package without an npm, pnpm or Yarn lockfile of its own, such as a workspace member the root lockfile installs. A patch's stripe-node upgrade still edits only the root `package.json`, so a TypeScript package's patched type check can fail on the new `apiVersion` until the patch upgrades the package itself.

## Check time limit

Each check, the baseline, the patched and each generated check, runs for at most `checkTimeoutSeconds` from `.refit.json`, a whole number from 30 to 1800, and 600 by default. Refit then stops the container and the check reports `Check exceeded <N> seconds`, which is an execution error, never a failure of the patch. The default replaces 120 seconds and comes from measured durations, one CPU per check:

- **GitHub Actions** (refit-bench run 40144503063, 249 affected repositories, 4-vCPU runners): the 106 baseline checks took 13.3 s at the median and 31.6 s at the 95th percentile, and the 103 patched checks at most 62.5 s. Two baseline test suites were still passing tests when the 120-second limit stopped them. Under 600 seconds (run 40155827550), one of them passed in 249 s on the original code and 250 s on the patch; the other was still passing tests at 600 s, so a repository like it sets a higher `checkTimeoutSeconds`.
- **Fly** ([P1](overnight/P1.md#what-should-the-120-s-check-limit-be-on-hosted-hardware)): a type check took 24.0 s and 29.5 s on performance-2x, and the same checks were estimated at 200 to 240 s on a throttled shared-cpu-2x.

The 300-second installation deadline stays: preparation took at most 51.6 s on Actions and 57 s on Fly performance-2x.

## stripe-node upgrade in a patch

When a Stripe patch for a TypeScript project moves `apiVersion`, it also moves the root `stripe` dependency to the release for the target version, because older type definitions accept only their own version. Refit edits only `package.json` and the root lockfiles, with the registry's SHA-512 integrity, and refuses anything it cannot reproduce exactly; the patch then stops for review rather than shipping a pin the old types reject.

- **npm:** lockfile versions 2 and 3, written with 2-space, 4-space or tab indentation and LF or CRLF line endings. The lockfile is rewritten in its own formatting.
- **pnpm:** lockfile v9 whose text round-trips byte for byte through pnpm's formatting, with `stripe` locked only by the root importer. The snapshot carries the optional `@types/node` peer the root installs, as pnpm writes it, and records only the old `stripe` reached are removed. pnpm 8's lockfile v6 is upgraded for a single project (no `importers`): the root `stripe` entry and its `/stripe@version(peers)` record are rewritten, packages only the old `stripe` reached are removed, and every package's `dev` and `optional` flag is recomputed from the new graph. Refit first recomputes the flags of the unchanged lockfile and refuses unless they match what pnpm recorded. Multi-document lockfiles and v6 workspaces are refused.
- **Yarn 1:** a root `yarn.lock` (LF line endings, no workspaces) whose `stripe` entry serves only the root declaration. The entry keeps the lockfile's registry host and SHA-1 fragment style; blocks only the old `stripe` reached are removed.
- **Several lockfiles:** a root that commits more than one of `package-lock.json`, `pnpm-lock.yaml` and `yarn.lock` has each one upgraded by its own rules above, because the package manager in use reads only its own, and the upgrade is kept when every lockfile succeeds and all of them lock the same `stripe` release. Otherwise, when preparation chose one of them (above), only that one is upgraded and the others stay as committed; the draft says the patch leaves them locking the older `stripe` and asks the owner to delete the lockfile their manager does not use. Without a choice, the first refusal, or the disagreement, is the reason. An empty lockfile is ignored.
- **No lockfile:** a root `package.json` with no lockfile at all (no npm, pnpm, Yarn or bun lockfile, no shrinkwrap) and no workspaces has only `package.json` changed, with `stripe` pinned exactly to the release: `npm install` resolves it afresh, and a `^` or `~` range could install a later release whose types accept only a newer API version. A declared `@types/node` must meet the release's optional peer range, read from the registry metadata (stripe 23.0.0: `>=20`, https://registry.npmjs.org/stripe/23.0.0, read 2026-10-25). The patch warning says the rest of the dependency tree is resolved at install time. Without lockfile resolution (below) preparation still needs a lockfile, so such a patch is not validated; with it, validation installs a `package-lock.json` Refit resolved, and the warning says so.

Every manager refuses a release that adds dependencies or required peers, an installed optional peer outside the release's range (stripe-node 23 needs `@types/node >=20`), and a `package.json` that declares `stripe` more than once.

**Types-only peers (founders' decision, 2026-10-27).** With lockfile resolution on, an `@types/*` package declared once in the root `devDependencies` with an exact, `^` or `~` version, and installed outside the release's optional `>=` peer range, is raised with `stripe` to the lowest version in that range, keeping its prefix (`"@types/node": "^18.19.0"` becomes `"^20.0.0"` for stripe 23.0.0). For npm, Refit re-resolves the committed `package-lock.json` with both declarations changed (below) and keeps the result only when every lockfile entry that changed is `stripe`, the raised peer, or a package only they reach: `@types/node` 20 depends on `undici-types ~6.21.0` where 18 used `~5.26.4` (registry.npmjs.org, read 2026-10-27), so `undici-types` moves with it, and a package anything else also reaches refuses the upgrade. The re-resolved lockfile is part of the patch and keeps the committed lockfile's root names (npm otherwise names a project without a `package.json` name after the sandbox directory). The draft's key changes and review list name the bump and the peer range it comes from, and the warning records the version npm locked and the cutoff. Without a committed lockfile only `package.json` changes. Any other conflicting peer, an `@types/*` package in `dependencies`, and pnpm and Yarn lockfiles keep the refusal. The patched checks then decide as for every upgrade: a type check with new errors is a regression. A reset registry connection is retried twice. Validation then installs the patched lockfile frozen in Docker, so the package manager itself has the last word.

stripe-node 22.4.0 added `OtherString` to every open enum (`Stripe.Price.Type` became `'one_time' | 'recurring' | OtherString`), so code that assigns these values to its own narrower types stops compiling after an upgrade across that release. When validation compares type errors and every error the patch introduced is one of those shapes, Refit restores the known values at the reported positions and reruns the checks before any AI repair: `Extract<Stripe.X.Type, keyof Stripe.X>` for an index, and `Extract<Stripe.Price.Type, 'one_time' | 'recurring'>` for a field or a read assigned to one. The known values come from the stripe@23.0.0 declarations ([`stripe-open-enums.json`](../pipeline/stripe-open-enums.json), generated by `scripts/stripe-open-enums.mjs`; top-level resources only). The repair is kept when the checks then pass. Before an AI repair of a rules patch, it also applies when only some introduced errors have those shapes, and it is kept if the checks then fail only on the errors it left; the model repairs those on the restored code, and the AI guards treat the restore as a rule edit. Either way the PR says so. Runtime code is unchanged, so a value Stripe adds later still reaches the code unchecked, as before the upgrade.

## Lockfile resolution for validation

Founders' decision (2026-10-27): a networked lockfile-resolution step may run before, and separate from, the offline validation, which stays offline. It is on by default; `REFIT_LOCKFILE_RESOLUTION=off` turns it off (the benchmark's `--resolve-lockfiles` still sets it on explicitly). When preparation of a root npm project refuses because it commits no lockfile (`no-lockfile`), its `package-lock.json` is out of sync with `package.json` (`lockfile-out-of-sync`, from Refit's check or from `npm ci`) or has entries without integrity (`lockfile-integrity`), Refit resolves a lockfile in its own container (`pipeline/lockfile-resolution.ts`):

- The container receives only `package.json` and, for an out-of-sync lockfile, the committed `package-lock.json` as the starting point, so locked versions that still satisfy `package.json` stay. A lockfile without integrity is not a starting point: its versions cannot be verified. The repository's `.npmrc`, `.env` files, credentials and code never enter it; user and global npm configuration are empty files.
- `npm install --package-lock-only --ignore-scripts --registry=https://registry.npmjs.org/ --before=<cutoff>`, with `--legacy-peer-deps` only when the committed `.npmrc` sets it. npm runs root lifecycle scripts even in lockfile-only mode unless told not to (npm 10.9.2 `lib/commands/install.js`), so `--ignore-scripts` is required.
- The cutoff is the repository's last commit date (the committer date). A declaration whose lowest version was published later, such as the stripe release a patch pins, is left out of a first pass and added back in a second pass that starts from the first pass's lockfile and is cut off at that version's publication time, so only it and what it newly needs resolve later than the commit. The patched side uses the original commit's date.
- The result goes through the ordinary preparation: every package must be a `registry.npmjs.org` tarball with SHA-256-or-stronger integrity, then `npm ci` installs it frozen with scripts off. A refusal there keeps the original reason first and appends why the resolved lockfile was refused.
- The resolved lockfile is used to validate only. It is not added to the pull request; the draft says the checks ran against a lockfile Refit resolved, as of which date, and which pins resolved later. `environment.json` records it as `resolvedLockfile`.

What still stops: pnpm and Yarn projects (pnpm has only a relative `minimumReleaseAge`, added in 10.16.0, and Yarn 1 has no lockfile-only mode, so neither can resolve as of a date), Bun lockfiles, several lockfiles, workspaces, nested packages, Git, local and URL dependencies (`non-registry-dependency`), and a committed `.npmrc` that sets a registry or credentials.

Unsupported workspace layouts, explicit local/Git/URL dependencies, private registries, tracked `node_modules`, shrinkwrap files, bundled lock records outside a verified registry ancestor, custom npm installation flags and packages requiring lifecycle builds fall back to the repository's own install. Refit's own preparation never enables lifecycle scripts. The supported preparation route is provider-independent, while SDK mapping, migration semantics and useful application checks still require verification.

## The repository's own install

When Refit's own preparation refuses for a repository-side reason, Refit runs the repository's own install in a build sandbox instead and validates offline on the result (founder decision, 2026-10-28). The customer configures nothing.

- **The install.** It comes from the root `Dockerfile`, the devcontainer, a CI workflow's install step, or else the lockfile's manager. Only a recognised `npm ci`/`npm install`, `pnpm install` or `yarn install` command runs; other steps are listed as skipped.
- **The sandbox.** Lifecycle scripts run as that install runs them, with no secrets. Egress goes only through an allowlisting proxy, to public registries and the hosts the repository's install files name.
- **The snapshot.** Every `node_modules` becomes the same dependency archive validation already unpacks, recorded with `kind: refit-repository-environment`.
- **When it fails.** An install that needs a private registry, a credential or an unnamed download host fails there. The draft is then published untested and says what Refit could not check. If the customer merged the optional Refit validation workflow, their own CI also runs the checks.
- **Turning it off.** `REFIT_REPOSITORY_INSTALL=0` keeps Refit to its own preparation.

How each step works, and what it cannot do, is in [customer environment](CUSTOMER-ENVIRONMENT.md).

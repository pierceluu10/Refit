# Pull request descriptions

Every Refit PR, whether a local `pull-request.md` or a published draft, follows one fixed template, [the agent PR template](PR-TEMPLATE.md). It's built by `createReviewArtifacts()` in `pipeline/review.ts` from Refit's recorded report and states only what Refit recorded or can check. There are no emojis, and each bullet is one sentence. Full evidence (commands, hashes, findings, warnings, coverage and check logs) stays in the local `report.json`.

## Title

Conventional Commits, under 70 characters, with no trailing punctuation: `fix(<scope>): <description>`. The scope is the integration ID, or the SDK package name without its npm scope, for example `fix(stripe): migrate removed Stripe API fields`.

## Body

A draft that needs review opens with what blocks the merge, one section for each: dependency preparation that failed, removed request parameters the patch still sends, a webhook endpoint version Refit cannot see, and **Usages left for you** (traced usages no rule migrated and reads Refit could not trace). The Reviewer Checklist at the end has one box per action.

| Section                          | Contents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Overview**                     | What the provider changed that this code uses (removed fields it reads, removed request fields it sends, retired endpoints it calls), and whether a deterministic rule or AI (with its model) migrated how many usages in how many files. When the migrated code still has some, it says "migrates N of M". It ends with links to the provider pages that document the change                                                                                                                                                                                                                                                                                                             |
| **API Impact & Spec Changes**    | Breaking changes: removed response fields the code reads, replacements, request-field renames, the `payment_method_types` card rule and retired calls with their endpoints. Database migrations and environment variables are always None                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Key Changes**                  | One line per changed file: the removed fields whose reads it migrates, with the Stripe page for that file's rule, the card rule's `allowed_payment_method_types`, the pinned API version it moves, or the SDK upgrade. Review lines follow: why each replacement was chosen (see below), item selection for subscription periods, and a major `stripe` upgrade with its changelog                                                                                                                                                                                                                                                                                                         |
| **Code Changes**                 | The changed lines with two lines of context, each labelled `file:line` and its enclosing function, up to 80 lines. New files, such as the generated helper, are named with a pointer to Files changed. Lockfiles are named, not shown                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Automated Verification Gates** | **Evidence Strength** first: the repository's test command (or another configured command) ran, but Refit does not measure what it reaches; type-checked only, so no code ran; generated stripe-mock checks only; no meaningful check (`node -e 0`); or none, because the checks did not pass. Then each check and its result on the original and migrated code in offline Docker. A check that failed is named with its side and exit code, a type check with the first type error the patch introduced, and a check that could not finish with Refit's reason. The body stays under 16,000 characters. Site lists show 25 entries and say how many more are in `report.json`. When a body is still too long, Refit cuts the code changes to 40 lines, then to 20 lines with 10 sites per list, then leaves them out, and says so under Code Changes. Model-fix drafts follow the same budget. [PR body examples](PR-BODY-EXAMPLES.md) shows each shape regenerated from stored results.

Hidden comments follow: the migration identity Refit uses to find its own open draft, the run ID and patch hash, the provider (`<!-- refit-provider: <id> -->`), the target API version (`<!-- refit-target: <version> -->`) and the commit Refit last pushed to the branch (`<!-- refit-pushed: <sha> -->`).

## One draft per target version

Refit keeps one draft per repository, base branch, integration and target API version (`draftKey()` and `publishFiles()` in `pipeline/publication.ts`). A provider whose contract keeps the same version is keyed by its breaking changes instead, so an upstream edit that changes none of them keeps the same draft. The branch name is derived from those alone, not from the commit, the run or the patch bytes, so a rerun, a retry or a push to the base finds the same draft. With the GitHub App, Refit then does one of these:

| What GitHub holds | What Refit does |
|---|---|
| No draft for this target | Opens one: a single commit on the validated base, as Refit Agent |
| Its open draft, same base and patch | Nothing. Before generation, a matching draft also skips AI and validation |
| Its open draft on an older base, or with an older patch | Validates the current base and replaces its own commit with one on the new base. It moves the branch only while the branch still points at the commit Refit last pushed (a lease, like `git push --force-with-lease`), then refreshes the title and description. Same pull request number. If someone other than Refit reviewed the replaced commit, a comment names the old and new commits and why |
| Its open `[Needs review]` draft, written by an earlier Refit release | Generates and validates it again, once per release, and updates it in place: a newer rule may migrate what the earlier release left. Once nothing is left for review, the title drops `[Needs review]` |
| A draft with commits a person added (or a merge or rebase of the base) | Leaves the branch and description as they are and reports it, before generation. If the base has moved under the branch, one comment on the draft says so and asks for the base to be merged in. Before generation it names the files where Refit's scan of the new base finds usages to migrate, and asks to check the draft covers each; during publication, the files Refit's current patch changes. Refit edits that comment when the base moves again. A push that lands while Refit is updating the branch loses Refit the lease and ends the same way. Refit reads the branch itself, not the pull request's reported head, which GitHub may update a moment late |
| A pull request someone else opened from the Refit branch | Leaves it to them |
| A draft a person closed without merging | Nothing: no reopen, no new draft for that target. Reopening it lets Refit update it again. A draft Refit closed itself, as superseded or resolved, is not a decline: if its target comes back, Refit opens a new draft |
| A merged draft | Nothing for that target. The watcher then moves its baseline to the target (see below) |
| Its open draft, and the base already sends the target and uses none of what it breaks (the customer migrated it by hand) | Closes the draft, then comments once with the reason; the run reports `up-to-date`. A draft a person reopens stays open |
| Its open draft, and the base still sends the old version but no longer has the usages the draft migrated | Closes the draft, then comments once with the reason; the run reports `draft-closed` |
| Another open Refit draft for this provider and integration on the same base, from an older target version | Nothing by default. With `--supersede-drafts` (owner decision, Pierce, 2026-10-24, board #300), comments `Superseded by #N` with the reason and closes it, once the new draft is up to date. Refit closes it first, then comments. A draft with commits a person added stays open, and so do one a person marked ready for review, one a person reopened after Refit closed it, one from an earlier release that names no provider or target, and one whose target is the same as or newer than this draft's, so a retried job for an older target never closes a newer draft. Versions are compared in natural order (`2025-03-31.basil` before `2025-04-30.basil`, `1.9.0` before `1.10.0`) |

The evidence marker at the end of the body names the Refit release that wrote it. The watcher runs each job that ended with an open draft once more after a Refit upgrade; a current draft is found before generation, so only a `[Needs review]` draft from an earlier release is generated and validated again (with `--ai-patch`, that spends the AI budget once per draft per release).

Refit recognizes its own commit by the draft's record of the last commit it pushed (`<!-- refit-pushed: <sha> -->`). Before a move, Refit re-reads the draft and adds the new commit to the record, so an interrupted run, or another Refit run updating the same draft at once, still recognizes the branch; after the move it writes the description and posts any reviewer notice at once. A draft from an earlier release has no record, and a branch with no open draft has none to read; there Refit falls back to one parent and the App bot as both author and committer, and leases the tip it read. It never merges, never marks a draft ready, and never writes to a draft a person closed. A run with a personal token cannot tell its own commit from a person's, so it reports an existing draft as it is and refuses to overwrite a branch without one. Other integrations in the same repository have their own drafts. Tests: `pipeline/draft-lifecycle.test.ts` runs each row against simulated GitHub with real Git objects.

## After the merge

Nothing affected means no pull request, comment or issue. A run whose code already sends the target and uses none of what it breaks reports `up-to-date` and exits 0, before any AI, validation or publication (`targetReached()` in `pipeline/migration-review.ts`).

When a watcher (`refit watch`, `refit serve` and the hosted worker) sees that state for the first time, it records the target as its new baseline (`state.baseline` and `snapshots/<hash>.baseline.json` in the watch state). The next release is then compared with that target, using the target as the API version, so the customer gets one draft per release and nothing in between. The advance needs all of these:

- every SDK client Refit can read sends the target version as a literal `apiVersion`. A client that sends none, and so uses the SDK's or the account's default, never counts, so its baseline never advances;
- Refit finds no use of what the target breaks, including reads it cannot trace;
- every breaking change outside the migration rules is a removed response field Refit searched the code for and found no read of, such as one the merged draft migrated. Any other (a newly required request parameter, say) still stops for review;
- no source file was skipped.

After the advance, the next run compares with the target under the `source-verified` policy: nobody attested the target as a pin, so the code's own literal declarations must match it on every poll.

Until the contract changes, later commits are quiet: the watcher reports the target as already processed (`up-to-date`) and runs nothing. A contract update that keeps the target's version (Stripe publishes these between releases) is compared with the advanced baseline like any other: with nothing affected, each new commit then stops as `needs-review`, before any AI or validation. A pin someone moved without migrating the code, or a read Refit cannot trace, still stops for review and leaves the draft open. For an approved repository, the enrollment check accepts a client pin equal to the watcher's last captured target or its advanced baseline (`watchedApiVersions()` in `pipeline/watch.ts`), so the merged pin no longer blocks the next poll. Any other pin still stops there. The committed `.refit.json`, baseline and approval stay as they are.

A new Stripe API version is a new target, even when the changes Refit maps are the same. If Refit's draft for the previous version is still open, the next release opens one cumulative draft from the code's current version. The older draft stays open unless the worker runs with `--supersede-drafts`, which closes it with `Superseded by #N`; otherwise close it yourself and merge the cumulative one. One exception has no automatic path: the newer release stops for review or fails its checks, so the older draft stays open, and someone merges that older draft. The code then sends a version that is neither the baseline nor the watcher's target, and enrollment stops on the pin. Approve a configuration whose baseline is the merged version.

A new release that arrives before the watcher sees the merged code is compared with the old baseline, and stops for review on the pin. A retry does not recover it: the watcher then accepts only the newer release's version, not the merged one. Until someone moves the committed baseline and `apiVersion` in `.refit.json` to the merged version (an approved target then needs a new approval), every poll stops there.

Tests: `pipeline/release-replay.test.ts` replays two releases through an approved `refit serve` target against simulated GitHub. Acacia → basil → endive use Stripe's published invoice excerpts and Checkout bodies shaped like Stripe's, with validation simulated by applying the real patch. It checks one draft per release, the advance after each merge, quiet polls in between, and one cumulative draft when the next release lands before a merge.

Tests: `pipeline/draft-lifecycle.test.ts` (closing a resolved draft), `pipeline/watch.test.ts` (the advance, carried over to a job machine) and `pipeline/repository-enrollment.test.ts` (the accepted pin).

## Commit message

The draft's single commit uses the PR title without `[Needs review]` as its subject. The body is plain text wrapped at 72 columns: the overview sentence, one line per changed file (up to 25), the check command and its result, `Needs review` when the draft needs it, each provider page as `Source: <url>`, and `Refit-Run:` with the short run ID (and `Refit-Integration:` for a collection). Model-fix commits list each edited line with the old and new model and the retirement date. Check logs never go into a commit.

## How "why this replacement" is decided

For each removed field, Refit names the replacement only if the patch actually reads it, and states the strongest evidence it holds, in this order:

1. **A configured rename rule** in the provider adapter (`propertyRenames`).
2. **The after contract's description** of the added field mentions the removed field. The description is quoted.
3. **An attached vendor note** mentions both fields. The sentence is quoted with the note's label and URL.
4. **Otherwise only the name and type:** "Nothing documents it as the replacement, so confirm it carries the same meaning."

Refit never states a reason it can't trace to one of these sources. Quotes are trimmed to 300 characters, and Markdown in them is escaped.

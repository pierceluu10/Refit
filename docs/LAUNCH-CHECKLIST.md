PP10 keeps this file current through the night. It tracks what stands between `main` and the first customer, following the five launch steps in `OVERNIGHT-AGENTS.md`. Statuses:

- **On main**: verified behaviour, cited from [Readiness](READINESS.md).

- **Blocked** or **Needs owner decision**: copied from the lane PR or found in review, with its reason.

## What blocks the first customer, in order

1. **Accepting a second account** (deferred by the owner on 2026-10-22: no design partner yet). PG10 (#177) adds `REFIT_HOSTED_ACCOUNTS`, caps and fair claiming. Its claim and webhook paths can still deadlock, and fairness has no concurrent test. Adding the first customer account stays an owner decision.
2. **Isolation between accounts.** PG3 (#176) now runs each job on its own Fly Machine behind `--job-machines` (off by default; CI green at `6bb61a8`), but a 429 without `Retry-After` retries after 0 ms, one malformed Machines API response ends the hosted loop, and the reaper can destroy another worker's new machine. Lifting the `REFIT_HOSTED_OWNER` restriction and publishing drafts from job machines are owner decisions. OG3 (#175) hardens the sandbox (its `--memory-swap` change is now pinned by a gated test); OG2 (#171) wrote the threat model.
3. **A store that is safe to deploy.** PP7 (#194) adds versioned migrations and outage survival, but its retention purge runs on every loop pass with no flag, so the first deploy starts irreversible deletion; and migrations are recognised by version number alone. Every other hosted lane must then append a migration. PP6 (#200) deletes delivery records together with their replay hashes after 30 days, so a captured signed delivery is accepted again, which undoes #171's replay fix.
4. **Inventory on install.** PG1 (#170): an unapproved repository can still make the worker read files outside its checkout (`.refit.json` symlink, `providerConfig` path), and a stopped re-scan erases the last complete inventory. Must merge after #177.
5. **Approval without the CLI.** PG2 (#196) approves from a GitHub issue (off by default; admins and maintainers only). Bot comments are refused with 422, `/refit revoke` waits for every queued job, and the issue is refreshed and reopened every polling interval.
6. **Following the App's lifecycle.** PP6 (#200) follows renames, transfers, archiving and deletion. A rename changes the key that #170's inventories reference (a foreign-key error once #170 merges); every event it does not handle is answered `ignored`, which would stop #192's push re-scans and #196's comment approvals; a re-created repository re-enrolls under its old approval; approvals follow renames without a new review (owner decision).
7. **What the customer is told.** PP8 (#197) now has `docs/INSTALL.md` and `docs/DATA-HANDLING.md`. Both say Refit stores no file contents, which becomes false when #170 stores source lines from unapproved repositories. Slack is missing as a recipient (#178), issues opened in unapproved repositories by #192 and #196 are not mentioned, and "no secrets" and "no other copies" are promises no code enforces. The fallback page still describes the allowed flow to not-allowed installers.
8. **Monitoring and the living report.** PG4 (#192) monitors inventoried repositories and opens alert and weekly digest issues (both off by default). A stopped re-scan drops a repository from monitoring, an erroring re-scan spends the daily cap every 10 minutes, and the digest reaches every exposed repository indefinitely. PG5 (#221) adds `refit report` and one report issue per repository behind `REFIT_HOSTED_REPORTS` (off), including unapproved repositories; every push re-scan rewrites the issue and posts a notifying comment, and closed issues keep being updated.
9. **Operating the service.** PP5 (#178) built read-only `refit hosted` commands and a runbook (owner-only commands unmarked). OP7 (#190) pins the hosted image and adds an npm audit gate; merging changes the image at the next deploy.
10. **Fix quality and benchmark trust.** Steps 4 and 5 improve what a customer receives; none blocks an install. But several lanes widen what runs or what is edited without a recorded decision: four new automatic Stripe edits (#201), the validation image chosen by repository files (#199), offline generators before every check (#186), two sandboxes at once on large hosts (#212), platform packages skipped by default (#213), and excluded paths leaving exposures (#198). Registry entries that are already past due (#184, #189, #202, #204, #206, #207) would fail `--fail-within` and open alert issues on the day they merge.

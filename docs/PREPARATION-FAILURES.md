# Dependency preparation and baseline failures

This page ranks every dependency-preparation and baseline-check failure in the committed Stripe and Shopify benchmark results by cause, and records what Refit now does about each cause: fix it, or stop with a named reason that tells the repository owner exactly what to change.

Everything here was measured locally on October 22, 2026, with no AI and no network access during checks. Data: [`2026-10-22-preparation-failures.json`](benchmarks/2026-10-22-preparation-failures.json) (preparation, one row per repository) and [`2026-10-22-baseline-failures.json`](benchmarks/2026-10-22-baseline-failures.json) (baseline checks).

## Method

**Preparation.** I collected every row whose outcome is `refused-for-validation`, `baseline-failed`, `patched-preparation-error` or `patched-baseline-failed` from the Stripe fix-rate (original, held-out, fresh), Stripe active and Shopify (original, fresh) result files: 45 distinct repositories. The committed reasons are cut to their first line, which for most install failures is only `npm dependency preparation failed (1). REFIT_NODE_VERSION=...`, and failed installs keep no log. So I reran `refit prepare --image node:22-alpine --json` on each repository's pinned clone at Refit `fb0143a` (`main`), one repository per Docker lock hold, and read the full errors. 42 had a local clone at the pinned commit. The two Shopify repositories without one are listed as not rerun.

**Baseline checks.** Baselines that fail are mostly hidden in the benchmark totals: with `compareTypeErrors`, a type check that reports errors before the patch still counts as passed, and only errors the patch introduces fail it. I read the baseline output of the latest local report for each of the 138 repositories that ran checks (115 from runs at Refit `6d4f38a`, the rest from later October 16 runs).

## Fixes

### Legacy capitalised registry names

npm refuses capital letters in new package names, but packages published before that rule keep theirs. pnpm lockfiles that lock `JSONStream` (7 of 126 benchmark pnpm lockfiles, a count not backed by a committed results file) were refused as if it were a local or Git source. Registry dependency names now accept capitals; workspace names, which are new packages, scopes and path checks are unchanged. In a replay of the input checks on the seven cloned repositories, five now pass, one moves on to a real lockfile mismatch and one to its conflicting lockfiles.

### Lockfiles written against a public npm mirror

`npm ci` now runs with `--replace-registry-host=always`, so npm fetches every locked tarball from `registry.npmjs.org` and checks it against the lockfile's integrity, whatever host the lockfile recorded. A `package-lock.json` resolved through `registry.npmmirror.com` or `registry.yarnpkg.com` is therefore accepted, and the mirror is never contacted. pnpm lockfiles still need `registry.npmjs.org` tarballs, because pnpm fetches the recorded URL itself.

### Empty ranges in published packages

npm reads an empty range as any version, and published packages declare them (`@tabler/icons-react` 3.36.1 declares `"@tabler/icons": ""`). Such a declaration inside a lockfile record is accepted; the lockfile still pins the installed version with its integrity. The repository's own `package.json` still needs a registry range.

## Named stops

A cause Refit's own preparation cannot handle stops with a name. `refit prepare`, validation and `refit doctor` all show it. The original message comes first and names the dependency, file or path. The stop's reason is recorded on the error (`DependencyPreparationError.stop`) and, for baselines, in the report (`validation.baselineStop`).

A stop names what Refit could not do, never a task for the customer (founder decision and clarification, 2026-10-28, [customer environment](CUSTOMER-ENVIRONMENT.md)). Drafts show it under "What Refit could not do". Validation does not stop at these preparation stops: Refit first runs the repository's own install in its build sandbox (`pipeline/repository-environment.ts`), and the action describes what is left only when that fails too. The draft is then published untested. If the customer merged the optional validation workflow, their CI adds evidence.

| Stop                               | When                                                                                                  | What the draft says Refit could not do                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `dependency-tree-too-large`        | The dependency archive exceeds the profile's limit, or the installer runs out of workspace space      | The installed dependencies do not fit Refit's validation sandbox, so none of its checks ran on this patch.    |
| `non-registry-dependency`          | A dependency comes from Git, a URL, a local path, a mirror or a private registry                      | Refit's own preparation and its build of the repository's own install both failed, so none of its checks ran. |
| `conflicting-dependency-files`     | Two lockfiles, a shrinkwrap, a pnpm hook or tracked `node_modules`                                    | As above.                                                                                                     |
| `unsupported-lockfile`             | No root `package.json`, an npm lockfile older than version 2, no root record, or over 20,000 packages | As above.                                                                                                     |
| `unsupported-workspace`            | Workspace layouts the installer cannot build from manifests alone                                     | As above.                                                                                                     |
| `no-tests-found` (baseline)        | The test command finds no tests (Jest, Vitest or Mocha says so)                                       | The test command Refit selected found no tests, so its checks gave no evidence on this patch.                 |
| `native-build-required` (baseline) | A native addon was never built because Refit's own preparation installs with scripts disabled         | A native addon was not built, so the checks could not run on this patch.                                      |

The repository-side reasons (`no-lockfile`, `lockfile-out-of-sync`, `lockfile-integrity`, `peer-dependency-conflict`, `dependency-archive-limit`, `preparation-failed`) also now say what Refit could not install instead of asking for a fix. The quoted refusal messages from the installers are unchanged diagnostics, and some still name the change that would fix them.

The preparation messages say "need the repository install" where they used to say "require a custom image".

The existing repository-side reasons (`no-lockfile`, `lockfile-out-of-sync`, `lockfile-integrity`, `peer-dependency-conflict`, `dependency-archive-limit`) keep their messages. By default a preparation failure caused by the repository's inputs or its install now publishes the patch untested (owner decision 1, 2026-10-24), including a patched lockfile from a stripe-node upgrade that cannot be installed after the original checks passed: these reasons say in the draft what Refit could not install, and every other such failure is recorded as `preparation-failed`, with absolute paths in its message replaced by `[path]`. Refit's own errors (a held state lock, a damaged dependency cache, a missing Docker image, an invalid setting, `docker run` itself failing with exit 125 or denied mounts, an unreachable Docker daemon, the host out of space in overlayfs, a container killed from outside (137, SIGTERM), and an unreachable package registry such as `EAI_AGAIN`) are not preparation results: the job fails and is retried. With `--publish-validated-only` a preparation failure stays a stop.

## Lockfile drift (Push 279)

`npm ci` installs the committed lockfile when a declaration's range changed but the locked version still satisfies it, when a declaration moved between sections, and when one was removed (npm prunes it): it builds the tree from the lockfile and fails only when a declaration is missing from it or locked outside its range (npm 10.9's `lib/utils/validate-lockfile.js` and Arborist's `dep-valid.js`). Refit accepts the same drift (L2 prep 3, `docs/overnight/L2-prep-3.json`): every installed package is still a committed lockfile entry checked against its integrity, and nothing the lockfile does not record is installed. `brandbite/brandbite` (pdfjs-dist pinned at the locked 4.10.38) and `eka0789/evofuture` (the lockfile record still lists socket.io and socket.io-client, which no source file imports; its CI runs `npm ci`) prepare. #289 had kept evofuture refused because O2 classified that refusal as correct; both repositories' own CI installs this lockfile with `npm ci`, which is what Refit now mirrors. Prereleases, tags and aliases are never compared. Every other drift refusal of the set keeps refusing, and the message names the declaration `npm ci` rejects:

- A declaration the lockfile never locked (`Amarnath0077/industrialstore-main`, `LDAWoo/webprodigies-plura`, `piyush805/miro-clone`, `helloworld9912/Stripe-Account-Migration`): installing would resolve a version nobody committed, for two of them the Stripe SDK itself.
- A locked version outside the declared range (`ArhanAnsari/InspireGem` declares next 15.0.3 and locks 15.0.1; `SergeySharipov/ai-companion-saas` declares 15.3.6 and locks 15.3.0; `baifan1366/project-management-system`, `RicardoGEsteves/next-digital-marketplace`, `Eziox-Development/eziox-web`): `npm ci` refuses it too.
- A pnpm specifier change (`Suhaib3100/online-compiler`): a frozen pnpm install requires every importer specifier to equal `package.json`'s (pnpm's `satisfiesPackageManifest.ts`).

## Conflicting lockfiles and pnpm patches (Push 279)

None of the 12 conflicting-lockfile refusals in run 40236299492 has both a `packageManager` pin and a CI install, so #324's choice never applied. Five commit one lockfile that matches `package.json` and one that does not (`LucasKlemke/doctor-reborn`, `saidMounaim/tick-event`, `omar99elnemr/Docubot` and `karljuhl/Club_Connect` with pnpm, `Yosef-Ali/compasstio-ai` with Yarn): the stale one's own frozen install rejects it, so no install of that commit can use it, and Refit installs the other; the draft says which and why. The other seven keep refusing: both lockfiles match (`cesarolvr/journeylog-app`, `avikalp987/quill`, `dheerajcl/Jynx2.0`, `ensarokumus/tldr-app`, `Librum-Reader/Librum-Website`, and `Ankit-Sharma1011/Quill`, whose pnpm pin has no CI install behind it), or both are refused first for a `link:` dependency (`passion-27/QuotesAI`).

`kondax-com/Bocker` pins no manager and patches `next`. Its `pnpm-lock.yaml` records the patch's SHA-256, which only pnpm 10 computes (pnpm 9 hashes patch files as base32), so its frozen install under the pnpm 9.15.9 fallback failed with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`. An unpinned lockfile that records patches now installs with pnpm 10.34.7.

## Needs owner decision

- **Generated clients, on by default (founder decision, 2026-10-28).** <a id="generated-clients-behind-a-flag"></a>The generators removed on 2026-10-22 are back and run before every check unless `REFIT_GENERATE_CLIENTS=0` (`--skip-generated-clients` on the Stripe benchmark) ([Dependencies](DEPENDENCIES.md#generated-clients)). Besides the exact `postinstall`, `prisma generate` now also runs, with no flags, for a repository that declares `@prisma/client` and commits a schema where `prisma generate` finds it, and Prisma 4's engine name is a placeholder too. Measured on l2-push-249 run 40552957597 (`3b5cb244`): 58 of 189 type checks report `@prisma/client` with no exported members, and 3 of 10 failing test baselines cannot load the client. With generation (run 40638306398 against main 40624045392), rows with that error fall from 73 to 2, outcomes are identical on all 249 and validated stays at 84 ([benchmarks](BENCHMARKS.md#runtime-stand-ins-and-generated-clients-october-28)).

- **Yarn 1 preparation space.** Decided by owner decision 3 (2026-10-24, Push 279): preparation and validation default to the 4 GiB profile (#303). Under it all five Yarn 1 repositories of the Push 279 set that ran out of the 2 GiB workspace prepare (refit-bench run 40142158182). Yarn 1 fetches every package its lockfile records, other platforms' optional binaries included, before it reads their `os` and `cpu` fields, so no install flag avoids that download; under the smaller `2g` profile they still run out of space.
- **Submodules.** Built for gitlinks that `.gitmodules` does not declare (Push 279, #289): such a gitlink has no URL, so every clone, CI run and deploy checks out an empty directory there, and validation reads the same empty directory. A submodule `.gitmodules` declares still refuses: its files are not in the commit, and Refit never fetches anything outside the checkout.
- **Peer dependencies missing from the lockfile.** Built in Push 279 as an extension of the 2026-10-20 ERESOLVE decision, announced on the board for Laptop 1 to confirm or veto: when `npm ci` reports the lockfile out of sync (`EUSAGE`), Refit retries once with `--legacy-peer-deps` on the same lockfile, as it does for `ERESOLVE`. npm validates the lockfile again without peer edges, so the retry installs exactly the locked tree, and a lockfile that is out of sync for any other reason still stops. The draft states it as it states every `--legacy-peer-deps` install. Cases: `muhallimir/ampertalent` (`@sentry/webpack-plugin` needs a `webpack` peer the lockfile never recorded) and `devczero/saas-pdf-analysis-dev` (`fdir`'s optional peer `picomatch ^3 || ^4` meets the hoisted `picomatch` 2.3.1).

### Proposals (need an owner decision, not built)

- **Version-only npm records (6 rows).** npm installs `name@version` from the registry with no integrity check. Refit could read each version's `dist.integrity` from registry.npmjs.org on the host and pin it before `npm ci` runs, which installs the committed versions with verified tarballs, but the integrity would come from the registry rather than the commit.
- **A `packageManager` pin as the other lockfile's refusal (Quill).** Treat "package-lock.json refused because `packageManager` pins pnpm" like an out-of-sync refusal when the pinned manager's lockfile is the one in sync and check selection runs that manager. npm itself would install package-lock.json (Corepack does not manage npm), so this rests on the owner's intent, not on what a manager refuses.
- **Dangling `link:` declarations (2 rows).** Drop nothing; install with the link left pointing at a missing directory, as pnpm does. Needs a reading of pnpm's behaviour on a missing link target.

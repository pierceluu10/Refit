# Dependency preparation and baseline failures

This page ranks every dependency-preparation and baseline-check failure in the committed Stripe and Shopify benchmark results by cause, and records what Refit now does about each cause: fix it, or stop with a named reason that tells the repository owner exactly what to change.

Everything here was measured locally on October 22, 2026, with no AI and no network access during checks. Data: [`2026-10-22-preparation-failures.json`](benchmarks/2026-10-22-preparation-failures.json) (preparation, one row per repository) and [`2026-10-22-baseline-failures.json`](benchmarks/2026-10-22-baseline-failures.json) (baseline checks).

## Method

**Preparation.** I collected every row whose outcome is `refused-for-validation`, `baseline-failed`, `patched-preparation-error` or `patched-baseline-failed` from the Stripe fix-rate (original, held-out, fresh), Stripe active and Shopify (original, fresh) result files: 44 distinct repositories. The committed reasons are cut to their first line, which for most install failures is only `npm dependency preparation failed (1). REFIT_NODE_VERSION=...`, and failed installs keep no log. So I reran `refit prepare --image node:22-alpine --json` on each repository's pinned clone at Refit `fb0143a` (`main`), one repository per Docker lock hold, and read the full errors. 42 had a local clone at the pinned commit. The two Shopify repositories without one are listed as not rerun.

**Baseline checks.** Baselines that fail are mostly hidden in the benchmark totals: with `compareTypeErrors`, a type check that reports errors before the patch still counts as passed, and only errors the patch introduces fail it. I read the baseline output of the latest local report for each of the 138 repositories that ran checks (115 from runs at Refit `6d4f38a`, the rest from later October 16 runs).

## Fixes

### Generated files, recreated offline before the checks

Preparation installs with lifecycle scripts disabled, and checks run on a clean checkout, so two kinds of file a developer's machine always has are missing in validation. Refit now recreates them inside each check's offline sandbox, before the configured checks, from committed inputs only ([`declared-generators.ts`](../pipeline/declared-generators.ts)). They run only with prepared dependencies; a custom image ran its own install.

- **Prisma client.** When the root `package.json` declares `"postinstall"` as exactly `prisma generate` (optionally `npx`, `--no-engine` or `--schema <relative path>`), Refit runs that command with the locked `prisma` CLI before the checks. Any other script, including `prisma generate` chained with other commands, runs nothing. Generation runs offline. Prisma's install scripts would download its native engines from `binaries.prisma.sh`, which preparation never runs and validation cannot reach, and `prisma generate` tries to download them when they are missing. So Refit points `PRISMA_SCHEMA_ENGINE_BINARY`, `PRISMA_QUERY_ENGINE_LIBRARY` and `PRISMA_QUERY_ENGINE_BINARY` at placeholders: the client is built from Prisma's bundled WebAssembly, loads and type-checks, and a query fails as it would with no database. On `Sanjdcool/ApanStack-Newsletter` (Prisma 6.19.1) plain offline generation fails on the download; with the placeholders it exits 0, `@prisma/client` loads its 64 models and `new PrismaClient()` constructs. Its exit code is recorded in the check's `generators` evidence, and the checks run whether or not it succeeds, so a failed generation is no worse than before.
- **`next-env.d.ts`.** When `next` is a dependency, `tsconfig.json` names `next-env.d.ts`, and the file is not committed, Refit writes the triple-slash references `next dev` and `next build` write (the core types, image imports, and the router compatibility types when `app` and `pages` coexist). It leaves out Next 15.5's reference to the build's own `.next/types/routes.d.ts`, which a clean checkout does not have.

Neither file enters the patch or the draft: the patch is computed from the repository copy, and both are written only in the sandbox's temporary workspace.

### Legacy capitalised registry names

npm refuses capital letters in new package names, but packages published before that rule keep theirs. pnpm lockfiles that lock `JSONStream` (7 of 126 benchmark pnpm lockfiles) were refused as if it were a local or Git source. Registry dependency names now accept capitals; workspace names, which are new packages, scopes and path checks are unchanged. In a replay of the input checks on the seven cloned repositories, five now pass, one moves on to a real lockfile mismatch and one to its conflicting lockfiles.

### Lockfiles written against a public npm mirror

`npm ci` now runs with `--replace-registry-host=always`, so npm fetches every locked tarball from `registry.npmjs.org` and checks it against the lockfile's integrity, whatever host the lockfile recorded. A `package-lock.json` resolved through `registry.npmmirror.com` or `registry.yarnpkg.com` is therefore accepted, and the mirror is never contacted. pnpm lockfiles still need `registry.npmjs.org` tarballs, because pnpm fetches the recorded URL itself.

### Empty ranges in published packages

npm reads an empty range as any version, and published packages declare them (`@tabler/icons-react` 3.36.1 declares `"@tabler/icons": ""`). Such a declaration inside a lockfile record is accepted; the lockfile still pins the installed version with its integrity. The repository's own `package.json` still needs a registry range.

### Limits

- Generators run only at the repository root and only for exactly the `postinstall` forms above. A workspace package's own `postinstall`, `prisma generate` chained with other commands, and other generators (`contentlayer`, `nuxt prepare`, `svelte-kit sync`) still do not run.
- Prisma 5 and 6 are covered. Prisma 4 (6 of 126 benchmark repositories that declare the generator) downloads a differently named engine, and Prisma 7 (9 of 126) was not tested.
- The registry mirrors accepted are `registry.npmmirror.com` and `registry.yarnpkg.com`, for npm lockfiles only, and rely on the image's npm honouring `--replace-registry-host=always`; I checked that `node:22-alpine`'s npm 10.9.9 does.

## Named stops

A cause Refit cannot handle stops with a name and the exact change that unblocks it. `refit prepare`, validation and `refit doctor` all show it. The original message comes first and now names the dependency, file or path. The stop's reason is recorded on the error (`DependencyPreparationError.stop`) and, for baselines, in the report (`validation.baselineStop`). The custom-image change they point to is the one the [billing example](../examples/billing-demo.refit.json) uses.

| Stop                               | When                                                                                                  | What to change                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dependency-tree-too-large`        | The dependency archive exceeds the profile's limit, or the installer runs out of workspace space      | In `.refit.json`, remove `prepareDependencies`, set `image` to a local image that already has the dependencies installed (for example in `/opt/app/node_modules`), and start `command` and `baselineCommand` with `ln -s /opt/app/node_modules node_modules && `. Dependencies in the image do not count against the sandbox workspace. |
| `non-registry-dependency`          | A dependency comes from Git, a URL, a local path, a mirror or a private registry                      | Depend on a version published to `registry.npmjs.org`, or use the custom image above.                                                                                                                                                                                                                                                   |
| `conflicting-dependency-files`     | Two lockfiles, a shrinkwrap, a pnpm hook or tracked `node_modules`                                    | Keep only the lockfile of the manager you use, or remove `node_modules` from Git, as the message names; or use the custom image.                                                                                                                                                                                                        |
| `unsupported-lockfile`             | No root `package.json`, an npm lockfile older than version 2, no root record, or over 20,000 packages | Commit a root `package-lock.json` written by npm 7 or later, or use the custom image.                                                                                                                                                                                                                                                   |
| `unsupported-workspace`            | Workspace layouts the installer cannot build from manifests alone                                     | Use the custom image.                                                                                                                                                                                                                                                                                                                   |
| `no-tests-found` (baseline)        | The test command finds no tests                                                                       | Set `command` and `baselineCommand` to checks the repository has, such as its type check.                                                                                                                                                                                                                                               |
| `native-build-required` (baseline) | A native addon was never built because install scripts are disabled                                   | Use the custom image.                                                                                                                                                                                                                                                                                                                   |

The existing repository-side reasons (`no-lockfile`, `lockfile-out-of-sync`, `lockfile-integrity`, `peer-dependency-conflict`, `dependency-archive-limit`) keep their messages, and they remain the only ones the `--publish-unresolved` waiver accepts (owner decision, #88).

## Needs owner decision

- **Yarn 1 preparation space.** All four Yarn 1 repositories that run out of space install trees of 607 to 989 MiB, which fit the default 1 GiB validation archive. They fail only because Yarn 1 keeps an unpacked copy of every package, including other platforms' optional binaries, in its cache inside the same 2 GiB workspace. Under the operator's `REFIT_VALIDATION_WORKSPACE=4g` profile, 3 of the 4 validated and 1 stopped for review (`2026-10-16-stripe-fixrate-yarn-4g-results.json`). A 4 GiB preparation workspace for Yarn 1 alone, keeping validation at 2 GiB, would recover them. That changes the preparation profile set in 0.28.0, so it is not built here.
- **Submodules.** `git archive` leaves a submodule's directory empty, so Refit could validate the rest of the repository; checks that need the submodule would then fail at baseline. Refit refuses submodules today, and accepting them changes what validation claims to have checked.
- **Peer dependencies missing from the lockfile.** `muhallimir/ampertalent` fails `npm ci` with `Missing: webpack@5.112.0 from lock file`: `@sentry/webpack-plugin` requires a `webpack` peer the lockfile never recorded, so the lockfile was written with `--legacy-peer-deps`, but no committed `.npmrc` says so. Retrying `npm ci --legacy-peer-deps` on the same lockfile would install exactly its packages, as the ERESOLVE retry does. The owner decision of 2026-10-20 covers only ERESOLVE, so this retry is not added.

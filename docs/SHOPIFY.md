# Shopify Admin API

Refit checks a Shopify app's Admin GraphQL usage against Shopify's published schemas, and moves the app's pinned API version only when every document it can read is proven to work on the target version. The migration is deterministic: no AI is involved, and nothing runs against a store.

## Contracts

Shopify publishes the Admin API as a GraphQL schema for each supported quarterly version (`2026-01`, `2026-04`, …). Save one per version:

```sh
refit shopify-snapshot --version 2026-01 --output refit/shopify-before.json
refit shopify-snapshot --version 2026-10 --output refit/shopify-after.json
```

The command introspects Shopify's public documentation proxy (`https://shopify.dev/admin-graphql-direct-proxy/<version>`). No store, credentials or store operation are involved. The snapshot records the version, the URL and a SHA-256 of the schema, and Refit refuses a snapshot whose content does not match its hash.

Refit also pins Admin and Storefront schemas in the repository, with deterministic diffs and quoted migration rules: [Shopify contracts and rules](SHOPIFY-RULES.md).

Only supported versions are published. Shopify serves a request for an unsupported version as the oldest supported version, so an app pinned to `2025-01` is answered by `2026-01` today. Refit therefore uses the oldest supported schema as the before contract for older pins, and says so in the report.

## What Refit reads

- **Clients:** Storefront API clients (Hydrogen's `storefront.query/mutate`, `createStorefrontApiClient(...).request`, `shopify.clients.Storefront`) are told apart from Admin ones. Their documents and `apiVersion` are listed in `shopify.storefrontDocuments` and never checked against or moved to the Admin contract. A Storefront document Refit cannot read is listed there too and named in the draft; it does not stop the Admin move, and the schema proof leaves Storefront documents out.
- **Admin clients:** `admin.graphql(...)` from `@shopify/shopify-app-remix`, `-react-router` and `-express` (`authenticate.admin`, `unauthenticated.admin`); `createAdminApiClient(...).request(...)` from `@shopify/admin-api-client`; `new shopify.clients.Graphql(...).request/query(...)` from `@shopify/shopify-api`. Clients other packages build for an Admin `graphql.json` URL count as Admin clients: `new GraphQLClient(url)` (graphql-request), `createGraphQLClient({ url })` (`@shopify/graphql-client`), urql's `createClient({ url })` and Apollo's `new ApolloClient({ uri })`, held in a `const` or a class's `this.client`; their `request`, `rawRequest`, `query` and `mutate` calls are read like `admin.graphql`. A client returned, exported or passed on stops at that line.
- **Documents:** literals and constants in scope or imported from another module (named or default exports, re-exports such as `export { QUERY as PRODUCT } from` and `export *`, including Remix-style `./shopify.server` paths), `await import()` destructuring, `${FRAGMENT}` interpolation of constant fragments, ternaries between documents, `{ query }` bodies, members of constant objects (`QUERIES.product`) and every element of a constant array looped with `for (const tier of TIERS)`. Constant numbers and booleans are folded in (`first: ${PAGE_SIZE}`). A `let` is read through every value assigned to it (`let query = A; if (x) query = B`); any other write (`+=`, `++`, destructuring) stops. A call to a repository function is read through what it returns (`admin.graphql(productsQuery(id))`), a class field through its initializer when it is `readonly` or private, or when no code assigns it and no other class declares it, and a template that only wraps a value (`` `#graphql\n${query}` ``) as that value. `#graphql` literals, `gql`/`graphql` tagged templates, imported `graphql(...)` documents (codegen client preset, gql.tada) and `.graphql`/`.gql` files no call reaches are checked too, as untraced documents. A fragment one document spreads and another file defines (once, under that name) is appended before validation. A runtime value inside a GraphQL string (`product(id: "gid://shopify/Product/${id}")`) cannot change what a document selects, so a placeholder stands in for it.
- **Helpers, callbacks and closures:** when the document is a parameter of a function, Refit follows that function to every call: named helpers (`adminQuery(admin, query)`) called in the same file or through named, namespace or re-exported imports; callbacks passed to a repository function (`fetchAll((query) => admin.graphql(query))`); `const` arrows passed on; and closures returned by a factory (`const request = createRequest(admin); request(QUERY)` or `createRequest(admin)(QUERY)`). An options parameter is followed by property (`options.query`, `({ query }) => …`, `const { query } = input`), a private method through `this.method(...)` calls in its class, a member of a local `const` object (`const client = { graphql: (query) => fetch(...) }`) through every `client.graphql(...)`, and a function a module exports through `const { name } = await import('./module')`. A local function nothing calls sends no document. A call site passing a runtime-built document stops at its own line. If the function leaves what Refit can follow (stored in an object Refit does not follow, passed to a package such as `Effect.fn`, reassigned, returned from an exported function nothing calls, or in a module loaded with `import()` other than by destructuring), some callers are unknown, so the run stops at that line. An exported function nothing in the repository calls stops too. Mocks and spies in test files do not stop the run; documents that tests pass are checked as fixtures, as before.
- **Pins:** `ApiVersion.<Month><YY>`, `apiVersion: 'YYYY-MM'` in files that use Shopify (directly, through `const` bindings and imports, or as the default of `process.env.NAME ?? 'YYYY-MM'`, whose move the draft names because the variable overrides it where set), `/admin/api/YYYY-MM/` URLs and `/admin/api/${VERSION}/` URLs whose version is such a constant, and `LATEST_API_VERSION`, which the locked `@shopify/shopify-api` release fixes (the constant was removed in 12.0.0). Pins in `.graphqlrc.*` are codegen configuration: they are moved with the runtime pin but never count as a conflict.
- **REST:** `admin.rest.*`, `shopify.clients.Rest` and `createAdminRestApiClient` clients and every `get`, `post`, `put`, `patch` or `delete` call on them, REST resource classes (`shopify.rest.Product.all()`, `new admin.rest.resources.Metafield(...)`), `/admin/api/<version>/*.json` URLs, and versioned URLs with a resource path before a substitution (`/admin/api/2024-01/products/${id}.json`). Each one is reported at its file and line with the HTTP method and path where the code states them: the `path` of a REST client call (a literal or constant), the operation of a resource class (`all`, `find` and `count` are GET, `delete` is DELETE, `save` is POST or PUT), and for a URL its path plus the method of the `fetch` or HTTP verb call it is passed to, directly or through a `const`. Substitutions show as `{id}`. The report lists them under `shopify.restCalls`, and `refit scan` prints them. A REST call whose endpoint, parameters, body keys and read fields the versioned REST contract keeps unchanged stays REST and moves with the version ([REST contract](SHOPIFY-REST.md#versioned-rest-contract)). Other REST reads that a documented (or AI-proposed and checked) mapping covers are rewritten as GraphQL Admin queries behind a local adapter, always as `[Needs review]` ([REST rewrites](SHOPIFY-REST.md)); every other REST call stops for review.
- **Raw GraphQL requests:** a URL to `/admin/api/<version>/graphql.json` is an Admin GraphQL call made without Shopify's clients. Refit reads the document of `fetch(url, { body: JSON.stringify({ query }) })` and `axios.post(url, { query })`, for the URL and every use of a `const` holding it, following `query` into helper parameters as for client calls. Any other body stops for review at that line.
- **REST:** `admin.rest.*`, `shopify.clients.Rest` and `createAdminRestApiClient` clients and every `get`, `post`, `put`, `patch` or `delete` call on them, REST resource classes (`shopify.rest.Product.all()`, `new admin.rest.resources.Metafield(...)`), `/admin/api/<version>/*.json` URLs, versioned URLs with a resource path before a substitution (`/admin/api/2024-01/products/${id}.json`), and versioned URLs whose whole path is a substitution (`/admin/api/2024-01/${path}`), which may name any resource. Each one is reported at its file and line with the HTTP method and path where the code states them: the `path` of a REST client call (a literal or constant), the operation of a resource class (`all`, `find` and `count` are GET, `delete` is DELETE, `save` is POST or PUT), and for a URL its path plus the method of the `fetch` or HTTP verb call it is passed to, directly or through a `const`. Substitutions show as `{id}`. The report lists them under `shopify.restCalls`, and `refit scan` prints them. They are review-only evidence: Refit never rewrites a REST call as GraphQL.
- **Raw GraphQL requests:** a URL to `/admin/api/<version>/graphql.json` is an Admin GraphQL call made without Shopify's clients. Refit reads the document of `fetch(url, { body: JSON.stringify({ query }) })` and `axios.post(url, { query })`, for the URL and every use of a `const` holding it, following `query` into helper parameters as for client calls. The options and the body may be `const`s or a ternary, and with an `application/graphql` content type the body is the document itself. Any other body stops for review at that line.
- **Webhook version:** `api_version` in `shopify.app.toml` (and `shopify.app.<name>.toml`) is listed under `shopify.webhookApiVersions` and named in the draft. Refit never moves it: handlers read the payload of that version.

## The rule

Each document is validated against both schemas with the standard GraphQL rules:

| Result                                                                                      | What Refit does                                                                           |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Valid on both, no selected field changes type                                               | Counts as proven for the target                                                           |
| Invalid only on the target, and documented rules fix it                                     | Edited by the rules (below), then counts as proven                                        |
| Invalid only on the target, with AI enabled and no rule                                     | AI rewrites it; kept only if Refit's checks below pass, and the draft is `[Needs review]` |
| Invalid only on the target (removed field, argument, enum value or type) otherwise          | Stops for review at the exact line                                                        |
| Invalid on the before contract too                                                          | Stops: the query already fails on every version Shopify serves                            |
| A selected field changes type (for example `Date` → `DateTime`)                             | Stops: returned values change shape                                                       |
| Built at runtime, sent by a function Refit cannot follow, or a fragment Refit cannot inline | Stops: the document cannot be checked                                                     |
| `#graphql` literal no Admin call reaches, invalid on both                                   | Noted as another Shopify API (Storefront, Customer Account, Partner), not Admin usage     |

A default after `||` or `??` (`options.apiVersion || '2025-01'`) is a pin the patch moves, and the draft names what overrides it. An environment variable with no default in code and the `unstable` version are left alone and named in the draft; they stop nothing. Pins are compared by the version Shopify serves: a pin older than the oldest supported version is served as that version, so several such pins do not conflict. Only when nothing stops does the rule move every pin to the target version. An `ApiVersion` enum pin is moved only if the locked `@shopify/shopify-api` release defines the target member (`October26` first ships in 14.0.0, `July26` in 13.1.0, `April26` in 12.3.0, `January26` in 12.1.0). Otherwise the run stops, because upgrading the SDK is a separate, major change. REST calls, several different runtime pins, and pins Refit cannot resolve also stop for review. Fields deprecated on the target are listed in the draft PR, not changed.

Validation grades the patch again on the patched code ([Shopify proof](SHOPIFY-PROOF.md)): without schema proof at the target it is grade D and `[Needs review]`, and Refit's own development store can raise it to grade A.

### Fallback to a supported version

When the move to the target stops only because the SDK the app has (or can be upgraded to) cannot name the target, or because documents break on the target itself, Refit runs again against each supported quarterly version between the oldest supported one and the target, newest first, and proposes the first move that passes every check, with the version and SDK moved together as for the target. Shopify supports each version for about a year, so the draft says which version it moved to instead of the target, why, and until when Shopify serves it (from the deadline registry). Each version's schema is the `<version>.json` beside the target snapshot (the benchmark's `snapshots/` directory), else Refit's cached copy in `~/.refit/contracts/shopify/`, downloaded once from Shopify's public documentation proxy. Validation checks the patch against that version's schema.

### Documented rules

`pipeline/shopify-document-rules.ts` applies the `auto` rules of the Admin tables in `data/rules/shopify/` (written by the rules lane, with Shopify's own sources) up to the target version. A `graphql-rename` rule names a schema coordinate: a renamed field is written as an alias `oldName: newName`, so the response keeps its keys and no code reading the payload changes; arguments, input fields and enum values are renamed in place; a replacement on another type is not applied. A `graphql-argument-drop` rule removes an argument only where the document sends exactly the value it names. Rules also fix documents that already fail on the oldest supported version (which Shopify serves today to older pins), as long as the rewrite validates on the target. A rule edits only values written in the document: where a variable carries a renamed enum or input type, the draft names it, and a variable whose input type loses a field or enum value, or gains a required one, between the two versions stops the run (the schema proof's input check), because Refit cannot see what the code sends. Each edit sits where graphql-js proves the parent type on the before schema. A field rename whose two fields have different types is refused. The edited document must validate on the target with no errors, and no other selected field may change type; otherwise nothing is edited and the document stops, with the reason. Edits ship only with the version move they are for, and an edit on a string literal whose escapes make it differ from its source is refused. Documents no in-place rule fixes go to the documented migrations next (`graphql-migration` rules and the unused-variable fix, [Shopify rules](SHOPIFY-RULES.md#migrations)), which also rewrite the call's variables and the code's reads of the response.

### AI rewrites

With `--ai-patch`, a document that breaks only on the target and that no rule fixes is sent to the model with its errors and the target types it touches (`pipeline/shopify-ai-rewrite.ts`, AI use 4). The rewrite is kept only when Refit checks deterministically that it parses and validates on the target schema, keeps every operation, operation name and variable definition, and returns every response path of the original with the same type (a nullable value may become non-null). The patch's generator is then `openai`, the draft is `[Needs review]` with the AI-written lines listed, and each attempt, its model and cost are recorded under `shopify.ai`. Only a document read from one literal or one `.graphql` file is rewritten.

With `--ai-patch`, an Admin call whose document Refit cannot read statically (built at runtime, passed through a table or function) is sent to the model with its file and the files that file imports (AI use 5, `aiReconstructDocument`). The model returns the document the call sends; Refit keeps it only when every operation, field, argument, alias, fragment and variable name in it is written in that code, and graphql-js validates it on both the before and the target schema. A kept reconstruction no longer stops the version move: it is recorded under `shopify.reconstructed`, quoted in the draft for the reviewer to confirm, and validated again by the schema proof at the call's line in the patched code. A refused one keeps the `shopify-graphql:unreadable` stop with the reason.

AI repair works on Shopify patches as on Stripe ones ([AI repair](AI-REPAIR.md)): when an SDK upgrade breaks the build, the model gets Shopify instructions and, on a repeated proposal, the installed `@shopify/*` declarations the tsc errors name.

A field rename is not inferred from a deprecation notice. Of the 401 fields deprecated in `2026-01`, 23 name a same-typed replacement that still exists in `2026-10`, but same type does not mean same value: `ShopifyPaymentsPayout.gross` points to `net`.

## Add the agent

```sh
refit agents --add shopify
```

This writes a `shopify` integration into `.refit.json` with `refit/shopify-before.json` and `refit/shopify-after.json` and the repository's check command. Save the two snapshots, review the command, run `refit doctor`, and approve with `refit enroll`. Validation then runs the app's own checks in offline Docker on the original and the migrated code, like every Refit migration.

## Local lab

`~/Repos/refit-shopify-lab` is a TypeScript app on `@shopify/shopify-api` 14.0.1, pinned to `ApiVersion.January25`. It lists and renames products through `shopify.clients.Graphql` with a shared fragment. Its tests replace the SDK's fetch with simulated Admin responses and fail on any unexpected request, so nothing reaches a store. End to end:

1. `refit agents` detects Shopify (locked 14.0.1) and `--add shopify` scaffolds the integration.
2. `refit run --integration shopify` finds both documents valid on `2026-10`, moves `ApiVersion.January25` to `ApiVersion.October26`, and runs `tsc` and the tests in offline Docker on both versions of the code: **validated**, with a draft PR description ready.
3. On the `scenario/removed-field` branch, a query of `deliverySettings` (removed in `2026-10`) stops for review at `app/delivery.ts:6`.

## Limits

- REST Admin reads are rewritten only for the endpoints and call shapes in [REST rewrites](SHOPIFY-REST.md); REST writes are never rewritten. `shopify-api-node` is detected but not migrated.
- Validation proves a document is well-formed against the schema, not that the app handles every new behavior (rate limits, new error codes, changed defaults). Application checks remain the evidence for behavior.
- Webhook subscriptions keep their own API version in `shopify.app.toml`; the draft PR names it and Refit does not move it.
- Storefront and Customer Account documents are classified, not checked: this pipeline compares Admin contracts.
- Documents built at runtime (interpolated cursors or filters outside strings, string builders) are not read, and neither are documents sent through class or object methods (`service.query(admin, QUERY)`), because finding their callers needs the receiver's type. Both stop for review at the exact line.

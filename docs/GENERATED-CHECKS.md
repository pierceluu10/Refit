# Generated Stripe checks

Refit validates a migration by running the repository's own checks before and after the patch. 83 of the 100 repositories in the [Stripe benchmark](STRIPE-BENCHMARK.md) have no real test script. Generated checks add version-specific Stripe evidence for them. Refit calls the migrated code paths against Stripe's own mock server, serving the old and new API versions, with networking still disabled.

## Configure

Add `generatedChecks` to a workflow or `.refit.json`:

```json
"generatedChecks": {
  "stripeMockImage": "stripe/stripe-mock:latest",
  "beforeFixtures": "./refit/stripe-2025-02-24.acacia.fixtures.json",
  "afterFixtures": "./refit/stripe-2025-04-30.basil.fixtures.json"
}
```

- `stripeMockImage` must already exist locally; Refit never pulls it. Pull the official image once with `docker pull stripe/stripe-mock:latest`. Evidence records its image ID and the hash of the binary used.
- The fixtures files come from the same `stripe/openapi` releases as your `before` and `after` contracts (`openapi/fixtures3.json` next to `openapi/spec3.json`). Both contracts must be JSON.
- Generated checks run in addition to `baselineCommand` and `command`, after those pass. Changing these settings changes the reviewed configuration, so `refit enroll` asks for approval again.
- They never raise the evidence grade above D: a changed file that only a generated check ran, and that neither the repository's tests reach nor a type check covers, leaves the validation at grade D, a `[Needs review]` draft (`pipeline/check-selection.ts`). Their placeholder fixtures check response shapes, so they are not the behaviour tests grade A requires.

## What runs

stripe-mock's README says it serves only the latest API version, but its `-spec` and `-fixtures` flags accept any release's published files. Refit verified this with the official image and Stripe's acacia and basil releases. Invoices had top-level `subscription` under acacia and `parent.subscription_details.subscription` under basil.

1. **Entry points.** For each confirmed finding, Refit takes the innermost exported function around it. That can be a function declaration, an exported `const` arrow or function expression, a default export, or a top-level function or `const` exported through an `export { … }` list, so findings inside inline callbacks count for their caller. A function qualifies if it has at most three parameters, each untyped or typed `string`. Other findings are counted as uncovered, never guessed.
2. **Runs.** Original code runs against stripe-mock serving the before contract and fixtures. Patched code runs against the after contract and fixtures. Each qualifying function is called with placeholder IDs (`refit_placeholder_1`, …), and its result is recorded separately, with whether it failed while loading its module, during the call, or by not settling within 10 seconds. No AI repair is attempted for generated checks.
3. **What counts.** A broken generated check never vetoes a patch:
   - **Counted, as a regression that fails validation:** a function that loaded and completed on the original code against the before-version mock and whose call then threw on the patched code against the after-version mock. Same function, same placeholder arguments, same deterministic fixtures: only the patch and the API version differ. The stop message names the function and its error, and nothing is published.
   - **Reported, never counted (status `unavailable`, with the reason):** generated checks that cannot be set up (no local stripe-mock image, a YAML contract, a Docker failure), a container that errors or times out, and a harness that stops before its last function (stripe-mock did not start, a crash, an exit from application code).
   - **Excluded, as before:** a function that fails on the original code cannot run in isolation, for example because it needs a database, and is listed with its error. If no function ran on both sides, the status is `not-runnable`.
   - **Reported, not counted:** a function that ran on the original side but does not load, or does not settle, on the patched side. After a stripe-node upgrade the patched dependency tree differs, and the harness loads modules differently from how applications are built, so that says nothing reliable about the patch; the repository's own checks cover module structure.
4. **Sandbox.** Both runs use the normal validation container: `--network none`, read-only root, no capabilities, non-root user, and the validation profile's workspace and memory. stripe-mock runs inside that container on `127.0.0.1`. A Node preload redirects HTTPS requests for `api.stripe.com` to it, and replaces the Authorization header with stripe-mock's standard test key. The redirect also handles the Stripe SDK writing request bodies only after `secureConnect`. The stripe-mock binary, contract, fixtures and generated harness are mounted read-only. There is no network, certificate or TLS change. Placeholder `STRIPE_SECRET_KEY`, `STRIPE_API_KEY` and `STRIPE_KEY` variables are set, and so are the credentials and service addresses the repository's own code reads from the environment when unset (names ending in `URL`, `URI`, `DSN` or `ENDPOINT` get a closed loopback URL, names ending in `KEY`, `SECRET` or `TOKEN` a placeholder string), so a client created at import, such as `createClient(process.env.NEXT_PUBLIC_SUPABASE_URL || '', …)`, does not stop the module from loading. Each side resolves imports with a map built from its own sources, so a patch that adds Refit's helper module loads.
5. **Stand-ins.** Application code often reads a database, a signed-in user or a service before its Stripe call, and stops there in the offline sandbox. Generated checks and behaviour tests give it stand-ins ([`runtime-stand-ins.ts`](../pipeline/runtime-stand-ins.ts)); the customer provides nothing, and none of them reaches the patch or the repository's own checks:
   - **`@prisma/client`** is served from the committed Prisma schema (`package.json`'s `prisma.schema`, `prisma/schema.prisma`, `schema.prisma` or `prisma/schema/*.prisma`): every model delegate answers with a placeholder record typed by the schema (`refit_placeholder_<field>` for strings, `1` for numbers, `false`, a fixed date, an enum's first value; relations only when `include`d), `findMany` with one record, `count` with 1, writes with the record merged with the written scalars. Enums and `Prisma` error classes are exported. No query engine, generation or database is involved.
   - **Services at the placeholder URL.** Requests through `fetch` to the closed loopback address Refit gives `*_URL` variables are answered instead of failing: Supabase's PostgREST returns one row with a `refit_placeholder_<column>` value per selected column (an object for `.single()`), writes return 201 or 204, Supabase auth returns a stand-in user, anything else `{}`.
   - **Session helpers.** `getServerSession` from `next-auth` and `next-auth/next`, and `auth` and `currentUser` from `@clerk/nextjs` and `@clerk/nextjs/server`, return a signed-in stand-in user; every other export of those packages is the installed one.

   No stand-in answers for Stripe: the `stripe` module is the installed SDK, and `api.stripe.com` still goes to stripe-mock, so a passing function proves its Stripe call ran against the mock. A function that fails on its own after a stand-in answered still fails. The report lists the stand-ins a run used (`validation.generated.standIns`). Stand-ins only change which functions run in isolation; generated checks still never raise the grade above D, and a function that ran on the original code and throws on the patched code is a counted regression, as before.

6. **Evidence.** The validation report records the status and its reason, the entry points, the functions not runnable in isolation, those unavailable on the patched side, regressions, uncovered usages, both results, the image ID, the binary hash and the contract and fixtures hashes. Benchmark rows keep the status, the reason and each function's error. The terminal summary and the PR's validation table show both runs; the PR says when generated checks were unavailable and that they count neither way. The PR text says the checks use placeholder data and check response shapes, not business behavior.

## Limits

- Stand-ins cover Prisma's default `@prisma/client` (not a custom generator `output` path), Supabase and other services reached through `fetch` at the placeholder URL (not `http.request`, axios or a database driver such as `pg`, Mongoose or Sequelize), and the NextAuth v4 and Clerk session helpers (not NextAuth v5's `auth()`, which each application creates). Behaviour tests use the stand-ins but do not yet record which ones ran.
- Only simple exported functions are called. Route handlers, class methods, and functions taking request objects or Stripe objects need application-specific arguments and stay uncovered; behaviour tests can cover them.
- stripe-mock fixtures use placeholder values, and they differ between versions, so return values are not compared. The check catches crashes and type errors on the new response shape, such as reading a property of a removed field, not wrong results.
- Code that does not crash on a missing field, for example by returning `undefined`, passes on both versions. Review stays necessary.
- Only the Stripe SDK's default Node HTTP client is redirected. Clients configured with a custom host, a custom HTTP client or `fetch` are not redirected, and fail in the offline sandbox.
- TypeScript files are transpiled in the sandbox by Refit's bundled TypeScript compiler, mounted read-only, rather than by Node's type stripping, which keeps imports of type-only names and fails at runtime. Imports resolve through a map Refit computes with its own verified resolver: extensionless relative paths, `index` files and `tsconfig`/`jsconfig` aliases. Imports a bundler resolves are retried as Node needs them: an import without a module extension (`next/server`, `./routeMatcher`, `./workerTimers.worker`) with `.js` or `/index.js`, and a JSON file imported without `with { type: 'json' }` (`import pkg from 'next/package.json'`) is served as a module whose default export is the data. CommonJS `require` of TypeScript and unverified alias configurations are not handled.

## Behaviour tests and grade A

Grade A needs behaviour tests: `node:test` files that a person or the behaviour-test generator writes for the repository (`pipeline/behaviour-tests.ts`).

- **Files.** `refit-behaviour/<name>.test.mjs` ES modules, 1 to 20, each at most 256 KiB. They are copied into the sandbox's copy of the repository root and import the code under test by a relative path (`../lib/billing.ts`), or through the repository's own aliases.
- **Runs.** The same unchanged files run with `node --test` on the original code against the before-version stripe-mock and on the patched code against the after-version stripe-mock, in the sandbox above, with the same preload: `api.stripe.com` goes to stripe-mock, TypeScript is transpiled, each side has its import map and the placeholder environment. Each test has 20 seconds. stripe-mock's own request validation is part of the signal: a removed parameter gets a 400 from the after-version mock.
- **Recorded requests.** Every Stripe request is recorded in order as `{ method, path, query, body, stripeVersion }`, with the query and form body decoded to plain objects (`a[b][0]=x` to `{ a: { b: ['x'] } }`). Tests read them from `globalThis.__refitStripe.requests` (and `globalThis.__refitStripe.reset()`) or `import { stripeRequests, resetStripeRequests } from 'refit:behaviour'`; `stripeRequests` is the same live array.
- **Changed Stripe lines.** For each source file the patch changes that imports the `stripe` package or holds a Refit finding: on the original side, the original line numbers of the lines the patch removes or replaces; on the patched side, the patched line numbers of the lines it adds. Refit writes whole-file hunks, so the lines come from a line diff of the two versions. Package manifests and Refit's generated helper module are not Stripe code: the helper runs through the changed call sites.
- **Coverage.** `NODE_V8_COVERAGE` records V8 block coverage in every test process. A changed line ran if any code that starts on it ran: the innermost V8 range holding the offset decides, so a branch not taken and a function never called count as not run. For TypeScript, offsets map back to source lines through the inline source map of a transpile identical to the sandbox's (its length is checked against V8's); for JavaScript, which runs as written, the offsets are those of the syntax nodes on the line. A line with no code (a comment, a type, a closing brace) is not executable and is listed separately. This needs no instrumentation in the test processes; Node writes the coverage of each process, `node --test` children included.
- **Grade A** needs every test to pass on both sides (none skipped, at least one), and every changed executable Stripe line to have run on both sides. Anything less keeps the grade the checks give (B, C or D), and `validation.behaviour.missing` says what was missing. Generated placeholder checks never give grade A.
- **What counts.** A test that passed on the original side and fails an assertion on the patched side is a regression and fails validation, named in the stop message. A side that does not finish, a test that cannot pass on the original code, a test file that does not load and a timeout are reported and never counted.
- **Evidence.** `validation.behaviour` records the status, the grade, what was missing, each test file's SHA-256, the changed, covered, missing and non-executable lines per side, each side's per-test results, and the stripe-mock image ID, binary hash and contract and fixtures hashes.
- **API.** `validateMigration({ …, behaviourTests: [{ path, content }] })` runs them on the patched copy unless its checks ran and failed, as the [writer](#behaviour-tests-written-by-a-model-opt-in) does (it needs `generatedChecks` for the stripe-mock image and fixtures; without them the behaviour evidence is `unavailable`). `runBehaviourTests({ tests, settings, image, root, original, patched, findings })` in `pipeline/validation.ts` runs them on prepared snapshots directly, and `behaviourGrade(result)` turns a result into `gradeEvidence`'s grade-A input.
- **Proof.** `pipeline/behaviour-tests.test.ts` runs the sandbox runner outside Docker against a simulated stripe-mock on snippets from three benchmark repositories: the correct patch gets grade A with every changed line covered on both sides, and a patch that keeps `payment_method_types` or reads a moved field only at its new location fails a test and counts. `pipeline/behaviour-tests-docker.test.ts` (Docker-gated, run by refit-bench's `gated.yml`) does the same with the real stripe-mock image, stripe-node and Stripe's acacia and endive contracts.

## Real repositories

In refit-bench run 40144503063 (main `c65f169`, the 249 non-held-out repositories of `push-279-affected.json`), 94 validations ran generated checks, and 34 entry points in 32 repositories qualified. 1 ran on the original code. Of the 33 that did not: 19 failed to load on imports a bundler resolves (`next/server` 12, `next/headers` 3, `next/navigation` 1, `@clerk/nextjs`'s ESM `./routeMatcher` 3), which the extensionless retry addresses; 9 created a client at import from an unset variable (Supabase 8, a Stripe key under another name 1), which the placeholder environment addresses; 4 need a request or response object a placeholder cannot stand in for; 1 needs a Prisma client that was never generated. Measured on the 31 of those repositories in `docs/benchmarks/subsets/l2-generated-entry-points.json` (#288's base, before run 40153367553, after run 40155048976, no outcome or grade changed): of 27 entry points, 3 loaded on the original code before and 12 after, and 1 ran on both sides before and 2 after. Of the 15 that still do not load, 10 import a Prisma client that was never generated (`prisma generate` needs a network), 2 validate their environment with a schema, 2 import React's `cache`, which only the React build Next.js bundles exports, and 1 parses the placeholder URL as a database dialect. Of the 10 that load and then throw, 6 need a database, 3 a request, response or framework context, and 1 calls `require` in code the sandbox runs as an ES module. On all 249 repositories (#288's base, before run 40155034890, after run 40161175319), entry points loaded 4 → 13 of 29 and ran on both sides 1 → 2, and one validation is no longer vetoed: brunobola-portfolio/GitHub-Repo-Manager's checks passed on both sides, but its configuration validation exited the generated harness at import, which used to fail the validation; it now passes at grade B with the generated check reported as unavailable. Generated checks reach little application code; behaviour tests are the way to grade A.

The lab also covers a TypeScript module that imports its client through an extensionless `@/client` alias. On the Stripe benchmark, 5 of 6 deterministically patched repositories have an entry point. Under the then-default 256 MiB archive limit none could run; with the 2 GiB profile (now the default) three load, and their helpers stop at creating a Supabase client, so they are excluded as not runnable in isolation. See [the benchmark re-run](STRIPE-BENCHMARK.md#re-run-with-ai-october-15). Generated checks fit libraries and service code more than full-stack apps today.

## Behaviour tests written by a model (opt-in)

`refit run --write-behaviour-tests` (and `benchmark:stripe --behaviour-tests`, which needs `--validate` and `--env` with `OPENAI_API_KEY` and `OPENAI_MODEL`) makes one OpenAI request per repository for node:test files that the behaviour-test harness then runs on both API versions (`pipeline/behaviour-tests.ts`; grade A when every test passes on both sides and every changed Stripe line ran on both). It never turns on AI patches.

- **What the model sees.** The original modules with confirmed findings, the modules they import (nearest first, up to 8,000 tokens), the findings, the contract excerpt for them (the removed field or parameter and what the after contract adds beside it), both versions, the harness contract, and two owner policies: never assert that a removed request parameter is absent, and test webhook handlers with a payload in the old shape too. It never sees a patch or any AI output: the request is built before any proposal exists. The files are sent to OpenAI.
- **What is refused.** Every file is dropped, with the reasons recorded, when any file is outside `refit-behaviour/<name>.test.mjs`, imports anything but node builtins, `stripe`, `refit:behaviour` and repository files, calls `fetch` or opens a socket, starts a process, writes outside a `mkdtemp` directory under `os.tmpdir()`, skips or narrows tests, exits the process, or defines no test. A refused or failed answer is never regenerated.
- **When it runs.** On every patched copy of the repository whose code can load, whether or not the repository's own checks ran: after both checks pass, and also where the baseline failed or timed out (the patched checks are then not run). Never where the patched checks ran and failed, because that patch is not published. When the repository's dependencies cannot be prepared, the patch stays untested, and behaviour tests still run if every changed Stripe module loads with only `stripe`: each side installs stripe and the closure its own npm lockfile records, with the lockfile's integrity and scripts off, then runs offline. `validation.stripeOnly` says why that could not happen. Where the writer does not run, its record is `skipped` with the reason.
- **Dry run.** `refit run --write-behaviour-tests-dry-run` and `benchmark:stripe --behaviour-tests-dry-run` (which needs `--validate` and no key) build every request exactly as the real run would, send nothing, and record per repository `status: dry-run`, whether the real run would send it (`wouldRun`) and why not, with an estimate: input tokens at 3.5 bytes per token and the cost at `gpt-6.1-sol` prices with no output, a typical 8,000-token answer and the 25,000 output tokens every request reserves. Benchmark rows that never reach validation carry the record at the top level.
- **Spend.** Through the AI budget ledger like every other request: about $0.09 per repository at `gpt-6.1-sol` prices, at most $0.32 reserved per request. `validation.behaviourTestWriter` records the model, prompt hash, tokens, cost and each file's SHA-256.
